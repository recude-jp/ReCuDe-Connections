## 1. 背景と狙い

- 県人会・同窓会の総会や懇親会は、会員が実際に顔を合わせる最大の機会である。そこを、アプリでのつながりが生まれる場にする。
- 受付と各テーブルに、**NFC タグとQRコードを1つにした札（会場タグ）**を置く。スマホをかざすか、QRを読み取るとチェックインになる。
- チェックインした人は、「いま会場にいる人」「同じテーブルの人」を写真付きで見られ、共通点（同じ高校・部活・出身地など）が分かる。そこから名刺交換（F1）につなげる。
- イベントは、**ルートコミュニティ（県人会）と、各連携コミュニティ（同窓会）で別々に定義する。** 会員には、自分が所属するコミュニティのイベントだけを表示する。
- **その場でつながる名刺交換（qr-exchange-spec F1）は、イベントの中だけで使える。** つながりには、どのイベントで会ったかが必ず残る。連携コミュニティをまたいでつながるのは、ルートのイベントの中で行う。
- 管理者が作る総会・懇親会などの**公式のイベント**のほかに、正規の会員が同期会・飲み会などの集まりのために**プライベートイベント**を作れる（3-4）。プライベートイベントを作ってから名刺交換すると、つながりとその集まりが記録される。

## 2. 用語

- **公式のイベント**（`kind: 'official'`）: 管理者が管理画面で作るイベント。会場タグでのチェックイン、会場モード、5b章の機能を使える。
- **プライベートイベント**（`kind: 'private'`）: 正規の会員が作る、名刺交換のための集まり（3-4）。作成者と参加者だけに見える。
- **交換できる時間**: そのイベントで名刺交換できる時間。チェックインの受付時間（`checkInOpensAt`〜`checkInClosesAt`）と同じ。
- **イベントの所属**（`scope`）: そのイベントを主催するコミュニティ。ルートコミュニティ（`{ type: 'root' }`）か、連携コミュニティ（`{ type: 'community', communityId }`）。既存の `CommunityScope` と同じ型を使う。
- **会場タグ**: NFC タグを貼り、同じ URL のQRコードを印刷した札。種類は「受付」と「テーブル」の2つ。
- **チェックイン**: 会場に来たことの記録。会場タグか、管理者の操作で行う。
- **会場モード**: チェックインした人が使う、イベント当日の画面（いま会場にいる人・同じテーブルの人・共通点）。

## 3. イベントの所属と表示範囲

### 3-1. 所属

- イベントは、必ずルートコミュニティか、1つの連携コミュニティのどちらかに属する。
- 公式のイベントを作るのは、その所属の管理者とする。
  - ルートコミュニティのイベント: ルートの管理者（`roles.admin`）
  - 連携コミュニティのイベント: その連携コミュニティの管理者（`Community.adminIds`）と、ルートの管理者
  - 判定は既存の `requireScopeAdmin` を使う。
- 正規の会員は、プライベートイベントを作れる（3-4）。所属は常にルートコミュニティとする。

### 3-2. 表示範囲（誰に見えるか）

**自分が所属するコミュニティのイベントだけを表示する。**

| 会員の区分 | 見えるイベント |
|---|---|
| 正規の会員（`member`）で連携コミュニティに所属しない | ルートコミュニティのイベント |
| 正規の会員で、連携コミュニティにも所属する | ルートコミュニティのイベント＋所属する連携コミュニティのイベント |
| 連携コミュニティだけのメンバー（`community`） | 所属する連携コミュニティのイベントだけ（ルートのイベントは見えない） |
| ゲスト（`guest`） | ルートコミュニティのイベントで、「ゲストも参加できる」としたものだけ（3-3） |

- 上の表は公式のイベントのもの。プライベートイベントは、作成者と参加者にだけ見える（3-4）。
- この判定は、画面だけでなく、**セキュリティルールと Cloud Functions の両方で行う**（11章）。
- 一覧では、イベントごとに所属のロゴと名称（例:「○○高校 在京同窓会」）を表示し、どのコミュニティのイベントか分かるようにする。
- 見えないイベントの会場タグを読み取った場合は、イベントの内容を出さず「このイベントは、主催のコミュニティのメンバーだけが参加できます」と表示する（6-4）。

### 3-3. ゲストの扱い

- ルートコミュニティのイベントには、「ゲストも参加できる」（`guestsAllowed`、初期値: オン）の設定を設ける。総会・懇親会に非会員の若手を連れてくる場面を想定する。
- 連携コミュニティのイベントでは、その連携コミュニティのメンバー（区分を問わず）が参加できる。連携コミュニティにゲストの区分は無いため、この設定は無い。
- 当日、アカウントの無い人が会場タグを読み取ったときは 6-5 の扱いにする。
- ゲストは、公式のイベントに参加・チェックインできても、名刺交換（qr-exchange-spec F1）は使えない。

### 3-4. プライベートイベント

**狙い**: 公式のイベントの無い日でも、同期会・部活の集まり・飲み会などで名刺交換できるようにする。その集まりが、出会いの記録に残る。

**作れる人と所属**
- 作れるのは正規の会員（`member`。区分なしの昔からの会員を含む）だけ。ゲストと、連携コミュニティだけのメンバーは作れない。
- 所属は常にルートコミュニティ（`{ type: 'root' }`）とする。正規の会員はみなルートの会員なので、出身の連携コミュニティ（同窓会）をまたいで集まれる。
- 1人が持てる、終わっていない（終了時刻を過ぎていない、中止していない）プライベートイベントは3件まで。作成は1日に5件まで。

**内容**（作成画面は1画面で、すぐ作れるようにする）

| 項目 | 必須 | 説明 |
|---|---|---|
| タイトル | ○ | 例:「岐阜高校 昭和58年卒 同期会」。50文字まで |
| 日付・開始・終了 | ○ | 初期値: 今日、今の時刻から3時間。開始から終了までは24時間まで。開始は30日後まで |
| 場所 | | 文字で書く（例:「新橋 ○○」）。50文字まで |
| メモ | | 参加者に見える説明。200文字まで |

- 画像・定員の設定・参加費・申込・会場タグ・会場モード・5b章の機能は無い。
- 交換できる時間は、公式のイベントと同じく、開始の60分前〜終了の60分後とする（`checkInOpensAt`・`checkInClosesAt` を作成時に計算して持つ）。
- 状態は「公開」と「中止」だけ。作った時点で公開になる（下書きは無い）。

**参加の仕方**
- 事前の申込や招待は無い。作成者が名刺交換の画面でこのイベントを選んで自分のQRを見せ、読み取った正規の会員が自動で参加者になる（qr-exchange-spec 5-4 の6.）。
- 参加者も、このイベントを選んで自分のQRを見せられる。読み取った人も参加者になる（輪が広がる）。
- 参加者になれるのは正規の会員だけ。ゲストと連携コミュニティだけのメンバーは参加できない（読み取ると案内が出る）。
- 参加者は100人まで（作成者を含む）。

**見える人**
- 作成者と参加者だけ。イベント一覧（5-1）にも、他の会員には出さない。
- 詳細画面（`/events/:eventId`）で、タイトル・日時・場所・メモと、参加者（写真・名前）を見られる。参加者の一覧を見られるのは、終了から30日後まで（`attendeeListUntil`）。それより後は、出会いの記録（F3）のイベントの絞り込みからだけたどれる。
- ルートの管理者は、不正利用への対応のため、管理画面の「プライベートイベント」で一覧（タイトル・作成者・日時・参加者数）を見て、中止できる。参加者の名前とメモは見ない。

**編集と中止**
- 作成者は、終了時刻までタイトル・時刻・場所・メモを変えられる（交換できる時間は変更に合わせて計算し直す）。
- 作成者は、いつでも中止できる。中止すると、名刺交換QRを出せなくなり、まだ使われていない交換トークンも使えなくなる。すでにできたつながりと出会いの記録はそのまま残る。
- 参加者に通知はしない（作成・変更・中止のどれも）。

## 4. イベントの内容（公式のイベント）

| 項目 | 必須 | 説明 |
|---|---|---|
| タイトル | ○ | 例:「2026年度 定期総会・懇親会」 |
| 所属（scope） | ○ | 作成する管理画面の対象で決まる。作成後は変えられない |
| 日時（開始・終了） | ○ | |
| 会場 | ○ | 会場名・住所。地図のリンク（任意） |
| 説明 | | プログラム・服装・持ち物など |
| 画像 | | 1枚（一覧と詳細の上部に出す） |
| 定員 | | 空欄は定員なし |
| 参加費 | | 文字で書く（例:「会員 8,000円／35歳以下 3,000円」）。支払いはアプリの外（当日現金・振込） |
| 申込の締切 | | 空欄は開始時刻まで |
| 当日参加を受け付ける | | 初期値: オン。オンなら、申込をしていない人も会場タグでチェックインできる |
| ゲストも参加できる | | ルートのイベントだけ。初期値: オン |
| チェックインの受付時間 | | 初期値: 開始の60分前〜終了の60分後 |
| 参加者一覧を見られる期間 | | 初期値: 終了から30日後まで（7-3） |
| 状態 | ○ | 下書き／公開／締切／終了／中止 |

- 「下書き」は管理者だけに見える。「公開」にすると、表示範囲の会員に見える。
- 「中止」にすると、申込者に通知し、会場タグは使えなくなる。
- 締切は、申込の締切を過ぎたとき、または定員に達したとき（キャンセル待ちは受け付ける）に表示する。終了は終了時刻を過ぎたら自動で表示する（保存する状態は変えず、表示で判定する）。

## 5. 会員の画面

### 5-1. イベント一覧（`/events`、メイン機能「イベント」）

- 既存の仮画面を置き換える。
- 「これから」と「これまで」を切り替える。「これから」は開始日時の近い順、「これまで」は新しい順。
- 1件に表示するもの: 画像、所属のロゴと名称、タイトル、日時、会場名、自分の申込の状態（参加予定／キャンセル待ち／出席済み）。
- 所属で絞り込める（自分が所属するコミュニティの数が2つ以上のときだけ出す）。
- 当日（チェックインの受付時間中）のイベントは一番上に大きく出し、チェックイン済みなら「会場モードを開く」ボタンを出す。
- 自分が作った・参加したプライベートイベントも一覧に出す（「プライベート」の印を付ける）。交換できる時間中なら「名刺交換」ボタンを出す。
- 正規の会員には、一覧の上に「プライベートイベントを作る」ボタンを置く（3-4）。

### 5-2. イベント詳細（`/events/:eventId`）

- 4章の内容を表示する。
- 申込: 「参加する」ボタン → 参加予定（定員に達していればキャンセル待ち）。「参加をやめる」で取り消せる（キャンセル待ちの人が繰り上がり、通知する）。
- 申込の人数（「参加予定 48人／定員 80人」）を表示する。
- **参加予定の人**（5b-2）: 自分が申し込んでいれば、「参加予定の人を見せる」に同意した他の申込者を、共通点の多い順に見られる。申し込んでいない人には名前を見せない。ここから「会いたい」（5b-2）を送れる。
- 当日は「チェックイン」ボタン（会場タグを読み取る画面へ。6-3）と、チェックイン済みなら「会場モード」ボタンを出す。
- 「これまで」のイベントで出席した場合は、「この日に会った人」（F3 のつながり一覧をこのイベントで絞り込んだもの）へのリンクを出す。

### 5-3. 会場モード（`/events/:eventId/live`）

チェックインした人だけが開ける。大きな文字・大きな写真で、懇親会の場で片手で使える作りにする。

- **いま会場にいる人**: チェックイン済みの人を写真付きで一覧する（`hideFromList` の人は出さない）。並びは「自分との共通点が多い順」を初期値とし、「名前順」に切り替えられる。各人に、声かけ歓迎・世話役の印（5b-3・5b-4）と、話のきっかけ（5b-5）を表示する。
- **共通点のお知らせ**: 画面上部に「あなたと同じ高校の人が5人、同じ部活の人が2人、同じ市町村の出身の人が7人います」のように表示する。タップするとその人たちに絞り込む。
  - 共通点は、テナントのプロフィール項目のうち、本人が公開している項目どうしで判定する（相手が非公開にしている項目は使わない）。判定はクライアント側で行う。
- **同じテーブルの人**: テーブルの会場タグでチェックインした（またはテーブルを移った）とき、そのテーブルの人を一覧の先頭に分けて表示する。
- **テーブルの見え方**: 他の人がどのテーブルにいるかは、一般の参加者には見せない（自分と同じテーブルかどうかだけ分かる）。居場所が分かるのは、「会いたい」が成立した相手（5b-2）、話し相手の募集に応じた人（5b-3）、世話役（5b-4）だけとする。管理者は参加者画面で全員のテーブルを見られる。
- 各人の行には「つながっています」の印か、「名刺交換」ボタン（F1 の名刺交換画面を、このイベントを選んだ状態で開く。自分も相手もゲストでないときだけ）と「申し込む」ボタン（コネクト申請。`canDiscover` を満たすときだけ）を出す。
- 「一覧に自分を表示しない」の切り替え（`hideFromList`）を画面の下に置く。
- 会場モードを開いている間に名刺交換（F1）・名刺QR（F4）でつながった場合は、出会いの記録にこのイベントを自動で付ける（9章）。

## 5b. 会場で若手を孤立させない機能

### 5b-1. 狙いと考え方

- 年上の参加者が多い懇親会では、若手、特に知り合いのいない人や自分から話しかけるのが苦手な人は孤立しやすい。孤立した経験は、次のイベントに来ない理由になる。
- 打ち手の方向は、**若手に「話しかけさせる」のではなく、「話しかけてもらえる」状態をつくること**とする。場慣れした年上の参加者・世話役のほうが、声をかけるのは得意である。
- 4つの機能で構成する。

| ID | 機能 | 若手にとって | 年上の参加者・世話役にとって |
|---|---|---|---|
| A | 会いたい | 事前に「会いたい」と伝えておけば、相手が探しに来てくれる | 後輩から指名される。会場で相手がどこにいるか分かる |
| B | 話し相手の募集と声かけ歓迎 | 一人のとき、目立たずに助けを呼べる | 「声かけ歓迎」の印で、話しかけてよい先輩として見つけてもらえる。困っている若手のところへ行ける |
| C | ご紹介 | 世話役が引き合わせてくれる | 誰と誰を引き合わせるとよいか、アプリが提案する |
| D | 話のきっかけ | 相手との共通点と話題が分かる | 同じ |

- これらは LINE などのオンラインの連絡手段には無い、**リアルの場で出会いを生む機能**であり、このサービスの中心的な価値と位置づける。
- イベントごとに、管理者が A・B・C を個別にオン・オフできる（初期値: すべてオン）。D は常に使える。

**共通の前提**
- **若手**: テナントの設定「若手とみなす年代」（初期値: 30代まで）に当てはまる人。年代はプロフィールの自動計算の「年代」を使い、本人が非公開にしていれば使わない。
- **初参加**: そのテナントのイベントに、これまでに出席したことが無い人。チェックイン時に判定して参加者の記録に持つ（`isFirstTime`）。
- 若手・初参加の印は、本人と、声かけ歓迎・世話役の人だけに見える（一般の参加者の一覧には出さない）。
- 共通点・話題の判定に使うのは、相手が公開している項目だけとする。
- 監視の仕組みは作らない（「誰とも話していない人」を自動で検知するなどはしない）。助けを求めるのは本人の操作だけとする。

**共通点に使う項目の対応づけ（テナントの設定）**
- プロフィール項目はテナントごとに違うため、管理画面の「プロフィール項目」に、次の役割を項目に割り当てる設定を加える（`matchingFields`）。
  - 学校（例: 出身高校）、部活動、卒業年（期の差の計算に使う）、出身地、年代、話せること
- 東京岐阜県人会では、**「高校の卒業年」と「話せること」の項目が今は無い**ため、追加が必要（15章 要決定事項）。
  - 卒業年: 入力方法「選択式」で年を選ぶ。期の差（「20期上の先輩」）の計算に使う。
  - 話せること: 入力方法「複数入力」。例:「就活の相談」「金融業界」「起業」「岐阜へのUターン」「子育て」。会員検索の条件にも使える。

### 5b-2. A: 会いたい

**事前（申込後〜当日）**
- 申し込むとき、「参加予定の人に自分を見せる」を選ぶ（`showInPreview`、初期値: オン）。オフの人は、参加予定の人の一覧に出ない。
- イベント詳細の「参加予定の人」に、自分と共通点のある人を共通点の多い順に出す。上部に「あなたと同じ高校の先輩が3人参加予定です」のように要約する。
- 各人に「会いたい」ボタンを置く。押すと、送る理由を選ぶ（任意）:「同じ高校の先輩なので」「仕事の話を聞きたい」「就活の相談をしたい」「同じ地元なので」「その他（30文字まで）」。
- 相手に通知が届く:「若手の○○さん（○○高校 2018年卒）が、懇親会であなたに会いたいと言っています」。相手は「会いましょう」か「今回は見送る」を選ぶ。
  - **送った側には、見送られたことを伝えない。** 送った側の表示は「届けました」のまま変わらず、成立したときだけ「○○さんも会いたいそうです」と知らせる。断られる不安で送るのをためらわないようにするため。
- 誰でも誰にでも送れる（年齢で制限しない）。ゲストも送れる（コネクト申請ではないため。会場で出会うための機能に限る）。

**当日**
- 成立した二人がどちらもチェックインしたら、両者に通知する:「○○さんが会場に来ました。テーブル5にいます」。相手がテーブルを移ったら、居場所を更新する。
- 会場モードの上部に「会う約束」として成立した相手を並べ、写真と今いるテーブルを出す。会ったら「会えました」を押す（出会いの記録に残り、名刺交換を案内する）。
- 当日の会場モードからも「会いたい」を送れる。

**上限と受け付けの設定**
- 1人が1つのイベントで送れるのは5件まで。
- 受け取る側は、承諾待ちが10件を超えたら新しい「会いたい」を受け付けない（送る側には「届けました」と表示し、受け取る側への通知はまとめて1回にする）。
- 申込時・会場モードで「会いたいを受け付けない」を選べる（`meetRequestsEnabled`）。オフの人には「会いたい」ボタンを出さない。

### 5b-3. B: 話し相手の募集と声かけ歓迎

**声かけ歓迎の印**
- 申込時・チェックイン後に「若手や初めての方に声をかけます」を選べる（`welcome`）。選んだ人には、会場モードの一覧で「声かけ歓迎」の印が付く。
- 若手・初参加の人の会場モードでは、声かけ歓迎の人を一覧の先頭近くに出す（共通点の多い順の中で優先する）。
- 声かけ歓迎の人の会場モードには、「今日、初めて参加した若手」が分かるように印を出す。

**話し相手の募集**
- 会場モードの下に、控えめなボタン「話し相手を探しています」を置く。周りの人に見えても目立たない文言・見た目にする。
- 押すと、今いる場所を確かめる（テーブルでチェックインしていればそのテーブル。違えば選び直せる。「受付付近」「その他（10文字）」も選べる）。一言を添えられる（任意。例:「就活中です」）。
- 知らせが届く相手: そのイベントの**世話役**（5b-4）と**声かけ歓迎**の人。同じテーブルの人を優先し、最初は近いテーブル（番号の近い順）の歓迎の人と全員の世話役に送る。
  - 通知の文:「テーブル4の△△さん（初参加・20代・○○高校）が話し相手を探しています」と、本人の写真。
- 最初に「行きます」を押した人が引き受ける。他の人の通知は「□□さんが向かっています」に変わる。
- 募集した本人には「□□さん（写真）が向かっています」と表示する。顔が分かるようにするため。
- 5分たっても誰も引き受けなければ、世話役全員にもう一度通知する（`escalatedAt`）。それでも無ければ、本人に「いま手が空いている人がいないようです。受付にお声がけください」と表示する。
- 本人はいつでも取り下げられる。会えたら、本人か引き受けた人が「会えました」を押す。
- 募集は1人1件まで。終わってから10分は次の募集をできない（いたずら防止）。
- 募集していることは、一般の参加者の一覧には出さない。

### 5b-4. C: ご紹介（世話役による引き合わせ）

**世話役**
- 管理者が、イベントごとに世話役（幹事・会場係）を会員から選ぶ（`hosts`）。世話役は会場モードで「世話役」の印が付き、話し相手の募集の通知を受け、ご紹介の提案を見られる。
- 世話役は全員のテーブルを見られる（引き合わせるため）。

**紹介の提案**
- 世話役の会場モードに「ご紹介」タブを置く。チェックイン済みの人から、引き合わせるとよい2人の組み合わせを、優先度の高い順に出す。
- 1件の表示:「A さん（初参加・20代・テーブル3）と B さん（声かけ歓迎・60代・テーブル7）― 同じ○○高校サッカー部、32期違い。B さんの話せること: 金融業界」
- 提案の優先度（Cloud Functions で計算する）:
  - 一方が若手または初参加で、もう一方が声かけ歓迎か世話役である組み合わせを優先する。
  - 共通点の重み: 同じ学校かつ同じ部活 ＞ 同じ学校 ＞ 同じ部活 ＞ 同じ出身地 ＞ 若手の話したいこと（5b-5）と先輩の話せることの一致。
  - 期の差・年代の差が大きい組み合わせ（縦のつながり）を少し優先する。
  - すでにつながっている組み合わせ、「会いたい」が成立している組み合わせ、どちらかが一覧に出ない設定（`hideFromList`）の人は除く。
  - その日すでに紹介された人は順位を下げる（同じ人に紹介が集中しないため）。
- 操作:「紹介しました」「今回は見送る」。「紹介しました」を押すと、2人に「□□さんの紹介で、○○さんと知り合いました」と通知し、出会いの記録の場面ラベルに「□□さんの紹介」を加える。
- 声かけ歓迎の人の会場モードにも「あなたに紹介したい方」として、自分を含む提案を3件まで出す（自分から声をかけに行けるように）。

### 5b-5. D: 話のきっかけ

- 会場モードの一覧と、相手の詳細に表示する。
- **共通点の要約**: 「同じ○○高校・サッカー部（32期上）・同じ岐阜市の出身」。期の差は、卒業年の項目が両者にあるときだけ出す。
- **話せること**: 相手のプロフィールの「話せること」。
- **今日話したいこと**: チェックイン後に任意で一言（30文字まで）を設定できる（`talkTopic`。例:「就活中です」「岐阜の地酒の話をしたい」）。その日のイベントの中だけで表示する。
- **話しかけるひと言の例**: 共通点から、テンプレートで1〜2文を出す（AI は使わない）。
  - 同じ学校:「○○高校の何年卒ですか？ 私は2018年卒です」
  - 同じ部活:「サッカー部だったんですね。当時の顧問の先生は…」
  - 同じ出身地:「岐阜市のどのあたりのご出身ですか？」
  - 話せることと話したいことが一致:「金融業界のお話を伺ってもいいですか？」
  - テンプレートは `src/app/core/utils/` に置き、既存の例文（message-templates）と同じく、テナントごとに差し替えられる作りにする。

### 5b-6. 通知の届け方

- 会場では即時性が大事なため、会場モードを開いている間は Firestore のリアルタイムの監視で、画面上部のお知らせとして出す（音とバイブレーションは端末の設定に従う）。
- 会場モードを閉じているときは Web Push で届ける。iPhone ではホーム画面に追加したアプリで通知を許可している場合だけ届くため、チェックイン時に通知の許可を案内する。
- 通知の種類（マイページの通知設定で個別にオン・オフ）: 会いたいが届いた／会いたいが成立した／会う約束の相手が会場に来た／話し相手の募集（世話役・声かけ歓迎の人だけ）／紹介された。

## 6. 会場タグとチェックイン

### 6-1. 会場タグ

- 会場タグは**コミュニティ（ルート・連携コミュニティ）ごとに持つ、使い回せる物理的な札**とする。イベントごとに作り直さない（NFC シールを毎回貼り替えないため）。
- 種類:
  - **受付**: チェックインする。
  - **テーブル**: チェックインし（まだなら）、そのテーブルに座ったことを記録する。テーブル番号（または名前、例:「3」「来賓席」）を持つ。
- URL: `https://{テナントのドメイン}/e/{タグコード}`（タグコードは推測されにくい英数字10文字。紛らわしい文字は除く。名刺QRと同じ作り方）
- 1枚の札に、NFC タグ（URL を書き込む）と、同じ URL のQRコードを印刷する。iPhone・Android のどちらも、かざすかQRを読めば同じ URL が開く。
- タップされたとき、サーバーは**そのコミュニティのイベントのうち、チェックインの受付時間中で、そのタグを使うことになっているもの**を探す（6-3）。
  - イベントの作成時、初期値ではそのコミュニティの有効な会場タグをすべて使う。イベントごとに使うテーブルを選び直せる（会場によってテーブル数が違うため）。
  - 同じ会場タグを、受付時間が重なる2つのイベントに割り当てることはできない（保存時に確かめる）。

### 6-2. 会場タグの準備（管理画面、7章）

1. 管理者が「会場タグ」画面で、受付タグ（1枚以上）とテーブルタグ（枚数を指定。番号は1から連番）をまとめて作る。
2. **札の印刷**: 札の PDF をダウンロードする（7-2）。
3. **NFC への書き込み**:
   - Android の Chrome では、管理画面から直接書き込める（Web NFC の `NDEFReader.write`）。画面の指示に従い、札の NFC シールに1枚ずつスマホをかざす。書き込み後、読み返して URL が正しいか確かめる。
   - iPhone ではブラウザから書き込めないため、管理画面に表示する URL を、市販の NFC 書き込みアプリで書き込む手順を案内する。
   - 推奨する NFC シール: NTAG213 以上（URL は40文字程度で収まる）。
   - **書き込んだら、ロック（書き換え禁止）を推奨する。** ロックしないと、第三者が別の URL（偽サイトなど）に書き換えられるため。管理画面の書き込み機能では「書き込み後にロックする」をオンを初期値にする（Web NFC の `makeReadOnly`。非対応なら案内のみ）。
4. 札をなくした・壊れた・いたずらされたときは、その会場タグを「使えなくする」にして、新しい会場タグを作り、札を作り直す。

### 6-3. チェックインの流れ（会員）

**読み取りの入口**
- **札にスマホをかざす／カメラアプリでQRを読む**: ブラウザで `/e/{タグコード}` が開く。
  - ログインしていなければ、ログイン画面に移る。パスキーを使っていれば、顔認証などですぐにログインできる（パスキーは端末のブラウザとホーム画面のアプリで共有される）。ログイン後に `/e/{タグコード}` に戻ってチェックインする。
- **アプリ内で読む**: イベント詳細の「チェックイン」ボタン、または F1 の「相手のQRを読み取る」で札のQRを読む。Android では、同じ画面で NFC の読み取り（Web NFC の `NDEFReader.scan`）も待ち受ける。iPhone のホーム画面のアプリでは NFC を読めないため、QR を読むか、ブラウザからかざす。

**処理**（Cloud Functions `checkIn({ tagCode })`）
1. タグコードから会場タグ（テナント・所属・種類・テーブル）を解決する。使えなくなったタグは「この札は使えなくなっています。受付にお声がけください」。
2. そのタグを使う、チェックインの受付時間中のイベントを探す。無ければ「いま受付中のイベントはありません」と、そのコミュニティの次のイベント（見える人にだけ）を表示する。
3. 読んだ人がそのイベントを見られるか（3-2・3-3）を確かめる。見られなければ 6-4。
4. 参加者の記録を作る・更新する（8章）:
   - 申込済み（参加予定・キャンセル待ち）→ 出席済みにする。
   - 申込なし → 「当日参加を受け付ける」がオンなら、当日参加として出席済みで作る。オフなら「このイベントは事前の申込が必要です。受付にお声がけください」。
   - すでに出席済み → チェックインの時刻は変えない。
   - テーブルタグなら、今いるテーブル（`seats/{memberId}` の `currentTable`）を更新し、テーブルの履歴に加える。会う約束の相手がいれば、新しい居場所を知らせる。
   - 初めてのチェックインなら、これまでの出席の有無から `isFirstTime` を決める。
5. 結果の画面: 「チェックインしました」（テーブルタグなら「テーブル3に着きました」）と、会場モードへの大きなボタン。2回目以降のタップ（テーブルの移動など）では、確認なしで会場モードを開く。

- 同じ人の `checkIn` は1分に10回までとする。
- 定員は、チェックインでは確かめない（会場に来た人は受け入れる。人数は管理者が把握する）。

### 6-4. 見られないイベントのタグを読んだとき

- イベントのタイトルや参加者は表示しない。
- 「このイベントは、主催のコミュニティのメンバーだけが参加できます」と、主催のコミュニティの名称を表示する。
- 連携コミュニティのイベントで、読んだ人がそのメンバーでない場合は、「受付で招待を受けてください」と案内する（同窓会の管理者が名刺QR・招待QRで招待すれば、その場で参加できる）。

### 6-5. アカウントの無い人が会場タグを読んだとき

- 会場タグは招待の代わりにならない（誰でも参加できてしまうため）。
- 表示: 「このイベントに参加するには、会員からの招待が必要です。受付か、お知り合いの会員に招待のQRを見せてもらってください」。
- 受付では、管理者（または受付係の会員）が招待QR・名刺QRを見せて、その場でゲスト（ルート）または連携コミュニティのメンバーとして参加してもらう。参加後にもう一度札をかざせばチェックインできる。

### 6-6. 管理者によるチェックイン

- スマホを持っていない・操作できない人のため、管理者がイベントの参加者画面（7-1）から、申込者の行の「出席」ボタンでチェックインできる（`checkedInVia: 'admin'`）。

### 6-7. 会場にいない人のチェックインへの対策

- 札の URL は写真に撮られて広まりうる。そのため次で抑える。
  - チェックインはイベントの受付時間中だけ。
  - チェックインできるのは、そのイベントを見られるログイン済みの会員だけ。
  - 管理者は参加者画面で不審なチェックインを取り消せる。
- 位置情報による確認は、利用者の負担とプライバシーの観点から行わない（Phase 1）。

## 7. 管理画面

### 7-1. イベント（`/admin/:scope/events`）

- 既存の管理画面の対象（`:scope` = root または連携コミュニティのID）ごとに、その所属のイベントだけを一覧・作成・編集する。連携コミュニティの管理者は、自分の連携コミュニティの分だけを扱える。
- 一覧: タイトル、日時、状態、申込数／定員、出席数。
- 作成・編集: 4章の項目と、使う会場タグの選択（6-1）、世話役の選択と、会いたい・話し相手の募集・ご紹介のオン・オフ（5b章）。
- 参加者画面（`/admin/:scope/events/:eventId`）:
  - 申込者・キャンセル待ち・当日参加・出席の一覧と人数。区分（会員・ゲスト・連携コミュニティだけ）を表示する。
  - 管理者によるチェックイン（6-6）と、チェックインの取り消し。
  - **出欠の CSV ダウンロード**（名前・区分・申込の状態・出席・チェックインの時刻）。事務局が総会の出席簿として使うため。電話番号などのログイン情報は含めない。
  - 当日の「いま会場にいる人数」と、テーブルごとの人数（受付の運営用）。
- 公開したとき、表示範囲の会員に通知するか選べる（初期値: 通知する）。

### 7-2. 会場タグ（`/admin/:scope/venue-tags`）

- 一覧: 種類、ラベル（受付／テーブル番号）、状態（有効／使えない）、最後に読まれた日時。
- 操作: まとめて作る（6-2）、ラベルの変更、使えなくする、NFC への書き込み（Android の Chrome のみ）。
- **札の PDF**:
  - テーブル用: A6 の三つ折りのテーブル立て（テント型）。両面に、テーブル番号（大きく）、QRコード（30mm 四方以上）、「ここにスマホをかざす」の NFC の目印、テナント（または連携コミュニティ）のロゴを入れる。NFC シールを貼る位置を点線で示す。
  - 受付用: A5 の札。「受付 ― スマホをかざしてチェックイン」とQR。
  - PDF はクライアント側で作る（名刺の裏面データと同じく `pdf-lib` を想定）。

## 8. データモデル

**追加**
- `tenants/{tenantId}/events/{eventId}`
  - kind（`official` / `private`）
  - scope（`{ type: 'root' }` か `{ type: 'community', communityId }`。private は常に root）
  - scopeKey（文字列。`root` か連携コミュニティのID。一覧の問い合わせとルールの判定に使う）
  - title、description、imagePath?、startAt、endAt、venue（name、address、mapUrl?）、capacity?、feeText?、applyDeadline?
  - allowWalkIn、guestsAllowed（ルートのみ）、checkInOpensAt、checkInClosesAt、attendeeListUntil
  - status（`draft` / `published` / `closed` / `cancelled`。終了は時刻で判定）
  - hosts（世話役の会員ID一覧）、features（meet、help、intro の各オン・オフ）
  - tagCodes（使う会場タグのコード一覧）
  - counts（applied、waitlisted、checkedIn。Functions が更新する。private は checkedIn に参加者数を入れる）
  - createdBy、createdAt、updatedAt
  - private で使う項目: title、startAt、endAt、venue（name だけ）、description、status（`published` / `cancelled`）、checkInOpensAt、checkInClosesAt、attendeeListUntil、counts、createdBy。それ以外の項目は持たない
- `tenants/{tenantId}/events/{eventId}/participants/{memberId}`
  - status（`applied` / `waitlisted` / `cancelled` / `walkIn`。private は `walkIn`）
  - appliedAt?、checkedInAt?、checkedInVia?（`nfc` / `qr` / `admin` / `exchange`。NFC か QR かは URL の付加情報で区別する。区別できなければ `tag`。`exchange` は名刺交換QRを読み取って、その場でチェックインしたもの）
  - joinedVia?（private だけ。`creator` / `exchange`）、invitedBy?（private で、読み取ったQRを見せていた人）。private では、参加した時刻を checkedInAt に入れ、参加者を「出席済み」として扱う（11章の参加者の読み取りの条件がそのまま使える）
  - hideFromList（初期値 false）
  - showInPreview（初期値 true）、meetRequestsEnabled（初期値 true）、welcome（初期値 false）、talkTopic?（30文字まで）、isFirstTime（Functions が設定）
  - displayName、photoPath?（会場モードの一覧用の写し。チェックイン時に書き、プロフィール変更時は `recomputeDerivedProfiles` で更新する）
- `tenants/{tenantId}/events/{eventId}/meetRequests/{fromId_toId}`（5b-2）
  - fromId、toId、reason?、note?、status（`pending` / `accepted` / `declined` / `met` / `cancelled`）、createdAt、respondedAt?
- `tenants/{tenantId}/events/{eventId}/helpRequests/{requestId}`（5b-3）
  - requesterId、location（テーブルのラベルか自由入力）、note?、status（`open` / `claimed` / `done` / `cancelled`）、claimedBy?、createdAt、escalatedAt?、closedAt?
- `tenants/{tenantId}/events/{eventId}/introductions/{aId_bId}`（5b-4）
  - aId、bId、reasons（共通点の文の一覧）、score、status（`introduced` / `skipped`）、by（世話役）、at。提案そのものは保存せず、呼び出しのたびに計算する
- テナントの設定: `matchingFields`（学校・部活動・卒業年・出身地・年代・話せること に対応する項目ID）、`youngAgeGroupMax`（若手とみなす年代の上限。初期値 30代）
- `venueTags/{tagCode}`（Cloud Functions 専用。ルールで読み書きとも禁止）
  - tenantId、scope、kind（`reception` / `table`）、label、tableNo?、active、createdAt、lastTappedAt?
- 一覧の問い合わせ用の複合インデックス: events の（kind, scopeKey, status, startAt）。自分が参加したプライベートイベントは、participants のコレクショングループの問い合わせ（memberId, checkedInAt）で探すため、participants に memberId の項目も持つ

**関連**
- 出会いの記録（qr-exchange-spec 6-1）の `eventIds` に、名刺交換したイベントが入る。場面ラベルにはイベントのタイトルが自動で入る。

- 型は `functions/src/models.ts` と `src/app/core/models/firestore.models.ts` の両方に加える（複製管理）。

## 9. 名刺交換・出会いの記録との連携

- 名刺交換（F1）は、いつもイベントの中で行う（qr-exchange-spec 5-1）。見せる側はイベントを選んでQRを出し、そのイベントは交換トークンに入る（`createExchangeToken({ eventId })`）。`exchangeConnect` はトークンからイベントを決め、読取者をチェックイン（公式）または参加者に追加（プライベート）してから、両者の出会いの記録の `eventIds` に加える。
- 会場モードから名刺交換の画面を開いたときは、そのイベントを選んだ状態にし、変えられないようにする。
- 名刺QR（F4）をイベントの中で読み取ったときは、`cardConnect` に `eventId` を渡す。両者がそのイベントの参加者なら `eventIds` に加える（qr-exchange-spec 7b-4 の7.）。
- F3 のつながり一覧の絞り込みに「イベント」を加える（場面ラベルより優先して表示）。
- 会場モードの一覧に、つながり済みの印を出す（自分の connections と照合）。

## 10. 通知

- 既存の Web Push の種類に次を加え、マイページの通知設定で個別にオン・オフできるようにする。
  - イベントの公開（管理者が「通知する」を選んだとき。表示範囲の会員だけに送る）
  - 前日のお知らせ（参加予定の人に。開始の24時間前を目安に、スケジュール関数で送る）
  - キャンセル待ちからの繰り上がり
  - イベントの中止（申込者に）

## 11. セキュリティルール

- `events/{eventId}`（kind が `private` のとき）
  - read: 作成者（createdBy）、参加者（`participants/{呼び出した人}` が存在する）、ルートの管理者。
- `events/{eventId}`（kind が `official` のとき）
  - read: status が `draft` 以外で、呼び出した人が表示範囲（3-2・3-3）に入るとき。`draft` は、その所属の管理者だけ。
    - ルート: 呼び出した人の区分が `member`（区分なしの昔からの会員を含む）、または `guest` で `guestsAllowed` が true。
    - 連携コミュニティ: 呼び出した人の `communityIds` に scope の communityId が含まれる。
    - 判定は、呼び出した人の members ドキュメントを `get()` して行う（既存のルールの判定関数に合わせる）。
  - write: 不可（Cloud Functions のみ）。
- `participants/{memberId}`
  - read（自分の分）: 本人。
  - read（他の人の分）: そのイベントに自分が出席済みで、`attendeeListUntil` より前で、相手の `hideFromList` が false のとき。加えて、その所属の管理者（private では、ルートの管理者も読めない。3-4）。
  - update（自分の分）: `hideFromList` だけ。それ以外は Cloud Functions のみ。
- `venueTags`: `allow read, write: if false;`
- `meetRequests`: 受け取った側（toId）だけが読める。送った側は Cloud Functions（`listMyMeetRequests`）経由で読む（見送られたことを伏せるため、`declined` を `pending` として返す）。書き込みは Cloud Functions のみ。
- `helpRequests`: 募集した本人と、そのイベントの世話役・声かけ歓迎の人（自分の参加者の記録で `welcome` が true）が読める。status が `open` 以外になったら、本人と引き受けた人と世話役だけが読める。書き込みは Cloud Functions のみ。
- `introductions`: そのイベントの世話役と管理者だけが読める。書き込みは Cloud Functions のみ。
- participants の他の人の `currentTable` は、一般の参加者には見せない。ルールで項目単位の読み取り制限はできないため、**テーブルの情報は participants から分け**、`events/{eventId}/seats/{memberId}`（currentTable・tables）に置く。seats は本人・世話役・管理者だけが読める。会いたいの成立相手と募集を引き受けた人には、Cloud Functions の通知と `getPartnerLocation` で居場所を渡す。
- participants の本人による更新を許す項目に、`showInPreview`・`meetRequestsEnabled`・`welcome`・`talkTopic` を加える（`talkTopic` は30文字以下）。
- ルールのテスト（エミュレータ）で、次を確かめる。
  - 連携コミュニティだけのメンバーが、ルートのイベントを読めない。
  - ルートだけの会員が、連携コミュニティのイベントを読めない。
  - ゲストが、`guestsAllowed` が false のルートのイベントを読めない。
  - 出席していない人が、参加者を読めない。
  - プライベートイベントを、作成者・参加者・ルートの管理者以外が読めない。ルートの管理者が、プライベートイベントの参加者を読めない。

## 13. 受け入れ基準

1. ルートの管理者がルートのイベントを、連携コミュニティの管理者がその連携コミュニティのイベントを、それぞれの管理画面から作成・公開できる。連携コミュニティの管理者は、他の連携コミュニティやルートのイベントを作成・編集できない。
2. 会員には、3-2 の表のとおり、自分が所属するコミュニティのイベントだけが一覧に出る。直接 URL やルールの問い合わせでも、見えないイベントは読めない。
3. 会員が申込み、定員を超えるとキャンセル待ちになり、取り消しがあると繰り上がって通知が届く。
4. 受付の札に iPhone をかざすと、ブラウザが開き（必要ならパスキーでログインし）、チェックインできる。札のQRをアプリ内で読んでもチェックインできる。Android の Chrome では、アプリ内で札にかざしてもチェックインできる。
5. テーブルの札でチェックインすると、会場モードで同じテーブルの人が先頭に出る。別のテーブルの札にかざすと、テーブルが移る。
6. 会場モードで、自分と共通点のある人の人数が表示され、タップでその人たちに絞り込める。相手が非公開にしている項目は共通点の判定に使われない。
7. 会場モードから名刺交換すると、両者の出会いの記録にそのイベントが付き、F3 でイベントで絞り込める。
8. 見られないイベントの札、受付時間外の札、使えなくした札を読んだときは、6章の案内が出て、何も記録されない。アカウントの無い人には、招待が必要と表示される。
9. 管理者が参加者画面から代理でチェックインでき、出欠の CSV をダウンロードできる。
10. 管理画面から会場タグをまとめて作り、テーブル立ての PDF をダウンロードできる。Android の Chrome で NFC シールに書き込み、ロックできる。
11. 申込者は、参加予定の人（公開に同意した人）を共通点の多い順に見て「会いたい」を送れる。見送られても、送った側の表示は「届けました」のまま変わらない。
12. 会いたいが成立した二人がチェックインすると、互いに相手のテーブルが通知される。成立していない人には他の人のテーブルが分からない（ルールのテストで確認）。
13. 「話し相手を探しています」を押すと、世話役と声かけ歓迎の人に写真付きで通知が届き、最初に「行きます」を押した1人が引き受ける。本人には向かってくる人の写真が出る。5分で引き受け手がいなければ世話役全員に再通知される。
14. 世話役の「ご紹介」に、若手・初参加の人と声かけ歓迎の人の組み合わせが、共通点の理由付きで上位に出る。「紹介しました」で両者に通知と出会いの記録が残る。
15. 会場モードの各人に、共通点の要約・話せること・今日話したいこと・話しかけるひと言の例が出る。非公開の項目は使われない。
16. 正規の会員がプライベートイベントを作り、名刺交換QRを見せると、読み取った正規の会員が参加者になり、つながる。作成者と参加者だけがそのイベントを一覧と詳細で見られる。
17. ゲストと連携コミュニティだけのメンバーは、プライベートイベントを作れず、参加もできない。
18. プライベートイベントを中止すると、名刺交換QRを出せなくなる。すでにできたつながりと出会いの記録は残る。ルートの管理者は管理画面で中止できるが、参加者の名前は見られない。

## 15. 要決定事項

1. **ルートと連携コミュニティの共催イベント**: 本書では、イベントは自分の所属するコミュニティの人にだけ見える。県人会が「同窓会メンバーも参加できる」イベント（SPEC.md 9章 C2 の案）を作れるようにするか。作る場合は、scope に「参加できる連携コミュニティ」の一覧を加える。
2. ~~**会員が企画するイベント**~~ → v0.3 で決定。正規の会員は、名刺交換のためのプライベートイベントを作れる（3-4）。申込・定員・会場タグのある、会員が企画する公開のイベント（グループ内のイベントなど）は、引き続き今後の検討とする。
3. **ゲストの参加**: ルートのイベントの `guestsAllowed` の初期値をオンでよいか。
4. **参加者一覧を見られる期間**: 初期値の「終了から30日後まで」でよいか。期間を過ぎた後は、出会いの記録（F3）からだけたどれる。
5. **受付係**: 管理者以外の会員に「受付係」の役割を与え、代理チェックインと招待をさせるか。
6. **参加費の管理**: 出欠の CSV に「支払い済み」の列を加え、管理画面で付けられるようにするか（アプリ内の決済はしない）。
7. **プロフィール項目の追加（東京岐阜県人会）**: 「高校の卒業年」と「話せること」を追加するか。追加しない場合、期の差の表示と、話せることによる提案は使えない。
8. **若手の基準**: 「若手とみなす年代」の初期値（30代まで）でよいか。同窓会ごとに変えられるようにするか。
9. **機能の名前**: 「声かけ歓迎」「話し相手を探しています」「会いたい」「ご紹介」「世話役」の呼び方。会長・若手の双方に違和感がないか、意見交換会で確かめる。
