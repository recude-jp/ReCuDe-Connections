## 1. 背景と狙い

**イベント**
- 県人会・同窓会の総会や懇親会は、会員が実際に顔を合わせる最大の機会である。そこを、アプリでのつながりが生まれる場にする。
- 受付と各テーブルに、**NFC タグとQRコードを1つにした札（会場タグ）**を置く。スマホをかざすか、QRを読み取るとチェックインになる。
- チェックインした人は、「いま会場にいる人」「同じテーブルの人」を写真付きで見られ、共通点（同じ高校・部活・出身地など）が分かる。そこから名刺交換（F1）につなげる。
- イベントは、**ルートコミュニティ（県人会）と、各連携コミュニティ（同窓会）で別々に定義する。** 会員には、自分が所属するコミュニティのイベントだけを表示する。
- 公式のイベントの申込・参加費の管理は、これまでどおりアプリの外（事務局の名簿・振込など）で行う。アプリには、管理者が**参加者名簿をインポート**する。参加者は名簿を見て、誰がアプリを使っていて、誰がもう会場に来ているかが分かる。
- 会場では、アプリを使っている人は名前を確かめるだけで自動でチェックインできる。アプリを使っていない人は、その場で参加を申し込み、イベントのホストが承認すると、アプリに登録されてチェックインできる。総会・懇親会を、アプリの利用者が増える場にする。
- 管理者が作る総会・懇親会などの**公式のイベント**のほかに、正規の会員が同期会・飲み会などの集まりのために**プライベートイベント**を作れる（5-4）。

**名刺交換と出会いの記録**
- 懇親会では、ふつうは名刺を交換する。名刺は名刺入れにしまわれ、そのまま忘れられることが多い。
- このアプリで「名刺交換」をすると、相手のプロフィール写真で顔を思い出せる。どこで会ったかも残り、何かのときにすぐ連絡できる。
- リアルの場で一度に多くのつながりができるので、アプリの中に最初から知り合いがいる状態をつくれる。非会員の若手が読み取れば、そのままゲストとして参加する入口にもなる。
- **その場でつながる名刺交換（F1）は、イベントの中だけで使える。** 公式のイベントか、プライベートイベントを選んでから交換する。つながりには、どのイベントで会ったかが必ず残る。
  - ゲストは名刺交換を使えない。
  - 連携コミュニティをまたいでつながるのは、ルートコミュニティ（県人会）のイベントの中で行う。
- 紙の名刺に印刷するQR（F4）で、名刺を渡すだけでアプリでのつながりにつなげられるようにする。
- 利用者の多くは60代以上である。名刺交換の操作は「QRを見せる」「QRを読み取る」の2つだけで完結させる（19章）。

## 2. 現状と課題（2026-10-14 時点の実装）

- メイン機能「イベント」（`/events`）は仮の画面だけで、中身は無い。
- 「つながる」の「招待」（`/connect`）に、会員ごと・招待先ごとに1つの長期有効なQRコード（`/join?code=…`）がある。
- **アカウントのない人**が読み取ると、ゲストとして参加し、招待した人とのつながり（承認済み）と1対1のトークが自動でできる（`joinAsGuest` → `connectWithInviter`）。
- **すでに会員の人**がルートコミュニティのQRを読み取ると、`joinAsGuest` は `alreadyJoined` を返し、ログインするだけで終わる。**つながりはできない。** ← 本仕様の名刺交換（F1）で解決する。
- QRコードは長期有効で、印刷したり写真に撮られたりして広まりうる。そのため「読み取っただけで、相手の同意なしにつながりが成立する」ようにはしない。

## 3. 用語

**イベント**
- **公式のイベント**（`kind: 'official'`）: 管理者が管理画面で作るイベント。会場タグでのチェックイン、会場モード、8章の機能を使える。
- **プライベートイベント**（`kind: 'private'`）: 正規の会員が作る、名刺交換のための集まり（5-4）。作成者と参加者だけに見える。
- **イベントの所属**（`scope`）: そのイベントを主催するコミュニティ。ルートコミュニティ（`{ type: 'root' }`）か、連携コミュニティ（`{ type: 'community', communityId }`）。既存の `CommunityScope` と同じ型を使う。
- **参加者名簿**（名簿）: 管理者がインポートする、公式のイベントの参加者の一覧（6-2）。1人1行。アプリを使っていない人も載る。
- **名簿との結び付け**: 名簿の行と、アプリの会員を結び付けること。結び付いた人を「アプリ登録あり」と呼ぶ。
- **ホスト**: イベントごとに管理者が選ぶ、幹事・会場係の会員（複数）。会場でのアプリ未登録の人の参加を承認する（9-5）。8章の機能でも役割を持つ。
- **会場タグ**: NFC タグを貼り、同じ URL のQRコードを印刷した札。種類は「受付」と「テーブル」の2つ。
- **チェックイン**: 会場に来たことの記録。名簿の行に付ける。会場タグ、名刺交換QRの読み取り、ホスト・管理者の操作、または会場での参加の承認で行う。
- **会場モード**: チェックインした人が使う、イベント当日の画面（いま会場にいる人・同じテーブルの人・共通点）。
- **交換できる時間**: そのイベントで名刺交換できる時間。チェックインの受付時間（`checkInOpensAt`〜`checkInClosesAt`。初期値: 開始の60分前〜終了の60分後）と同じ。この時間の外では、そのイベントで名刺交換できない。

**名刺交換と出会いの記録**
- **名刺交換QR**: 「名刺交換」画面に表示する、短時間だけ有効なトークン付きのQRコード。1つのイベントに結びつく。見せている本人が、その場でつながることに同意している印になる。
- **招待QR**: 既存の長期有効なQRコード（`/connect`）。
- **名刺QR**: 紙の名刺に印刷するための、会員ごとの長期有効なQRコード（`/c/{名刺コード}`）。招待QRとは別に持ち、招待QRを作り直しても使える。
- **出会いの記録**: 相手ごとに残す「いつ・どこで会ったか」と自分用のメモ。本人だけが見られる。
- **場面ラベル**: 出会いの記録に付く、会った場の名前（例:「2026年度 総会・懇親会」）。名刺交換ではイベントのタイトルが自動で入る。本人が F3 で追加・削除することもできる。

## 5. イベントの所属と表示範囲

### 5-1. 所属

- イベントは、必ずルートコミュニティか、1つの連携コミュニティのどちらかに属する。
- 公式のイベントを作るのは、その所属の管理者とする。
  - ルートコミュニティのイベント: ルートの管理者（`roles.admin`）
  - 連携コミュニティのイベント: その連携コミュニティの管理者（`Community.adminIds`）と、ルートの管理者
  - 判定は既存の `requireScopeAdmin` を使う。
- 正規の会員は、プライベートイベントを作れる（5-4）。所属は常にルートコミュニティとする。

### 5-2. 表示範囲（誰に見えるか）

**自分が所属するコミュニティのイベントだけを表示する。**

| 会員の区分 | 見えるイベント |
|---|---|
| 正規の会員（`member`）で連携コミュニティに所属しない | ルートコミュニティのイベント |
| 正規の会員で、連携コミュニティにも所属する | ルートコミュニティのイベント＋所属する連携コミュニティのイベント |
| 連携コミュニティだけのメンバー（`community`） | 所属する連携コミュニティのイベントだけ（ルートのイベントは見えない） |
| ゲスト（`guest`） | ルートコミュニティのイベントで、自分が名簿に結び付いているものだけ（5-3） |

- 上の表は公式のイベントのもの。プライベートイベントは、作成者と参加者にだけ見える（5-4）。
- この判定は、画面だけでなく、**セキュリティルールと Cloud Functions の両方で行う**（17章）。
- 一覧では、イベントごとに所属のロゴと名称（例:「○○高校 在京同窓会」）を表示し、どのコミュニティのイベントか分かるようにする。
- 見えないイベントの会場タグを読み取った場合は、イベントの内容を出さず「このイベントは、主催のコミュニティのメンバーだけが参加できます」と表示する（9-4）。

### 5-3. ゲストの扱い

- 誰が参加するかは名簿で決まる。ゲストも、名簿に載っていれば参加できる（総会・懇親会に非会員の若手が来る場面を想定する）。ゲストに見えるのは、自分が名簿に結び付いているルートのイベントだけとする。
- 連携コミュニティのイベントでは、その連携コミュニティのメンバー（区分を問わず）にイベントが見える。連携コミュニティにゲストの区分は無い。
- 当日、アカウントの無い人が会場タグを読み取ったときは 9-5 の扱いにする。
- ゲストは、公式のイベントに参加・チェックインできても、名刺交換（F1）は使えない（10-7）。

### 5-4. プライベートイベント

**狙い**: 公式のイベントの無い日でも、同期会・部活の集まり・飲み会などで名刺交換できるようにする。その集まりが、出会いの記録に残る。

**作れる人と所属**
- 作れるのは正規の会員（`member`。区分なしの昔からの会員を含む）だけ。ゲストと、連携コミュニティだけのメンバーは作れない。
- 所属は常にルートコミュニティ（`{ type: 'root' }`）とする。正規の会員はみなルートの会員なので、出身の連携コミュニティ（同窓会）をまたいで集まれる。
- 1人が持てる、終わっていない（終了時刻を過ぎていない、中止していない）プライベートイベントは3件まで。作成は1日に5件まで。

**内容**（作成画面は1画面で、すぐ作れるようにする）

| 項目 | 必須 | 説明 |
|---|---|---|
| タイトル | ○ | 例:「岐阜高校 昭和58年卒 同期会」。50文字まで |
| 日付・開始・終了 | ○ | 初期値: 今日、今の時刻から3時間。開始から終了までは24時間まで。開始は30日後まで |
| 場所 | | 文字で書く（例:「新橋 ○○」）。50文字まで |
| メモ | | 参加者に見える説明。200文字まで |

- 画像・定員の設定・参加費・申込・会場タグ・会場モード・8章の機能は無い。
- 交換できる時間は、公式のイベントと同じく、開始の60分前〜終了の60分後とする（`checkInOpensAt`・`checkInClosesAt` を作成時に計算して持つ）。
- 状態は「公開」と「中止」だけ。作った時点で公開になる（下書きは無い）。

**参加の仕方**
- 事前の申込や招待は無い。作成者が名刺交換の画面でこのイベントを選んで自分のQRを見せ、読み取った正規の会員が自動で参加者になる（10-4 の6.）。
- 参加者も、このイベントを選んで自分のQRを見せられる。読み取った人も参加者になる（輪が広がる）。
- 参加者になれるのは正規の会員だけ。ゲストと連携コミュニティだけのメンバーは参加できない（読み取ると案内が出る）。
- 参加者は100人まで（作成者を含む）。

**見える人**
- 作成者と参加者だけ。イベント一覧（7-1）にも、他の会員には出さない。
- 詳細画面（`/events/:eventId`）で、タイトル・日時・場所・メモと、参加者（写真・名前）を見られる。参加者の一覧を見られるのは、終了から30日後まで（`attendeeListUntil`）。それより後は、つながり一覧（F3）のイベントの絞り込みからだけたどれる。
- ルートの管理者は、不正利用への対応のため、管理画面の「プライベートイベント」（14-3）で一覧（タイトル・作成者・日時・参加者数）を見て、中止できる。参加者の名前とメモは見ない。

**編集と中止**
- 作成者は、終了時刻までタイトル・時刻・場所・メモを変えられる（交換できる時間は変更に合わせて計算し直す）。
- 作成者は、いつでも中止できる。中止すると、名刺交換QRを出せなくなり、まだ使われていない交換トークンも使えなくなる。すでにできたつながりと出会いの記録はそのまま残る。
- 参加者に通知はしない（作成・変更・中止のどれも）。

## 6. 公式のイベント

### 6-1. 内容

| 項目 | 必須 | 説明 |
|---|---|---|
| タイトル | ○ | 例:「2026年度 定期総会・懇親会」 |
| 所属（scope） | ○ | 作成する管理画面の対象で決まる。作成後は変えられない |
| 日時（開始・終了） | ○ | |
| 会場 | ○ | 会場名・住所。地図のリンク（任意） |
| 説明 | | プログラム・服装・持ち物など |
| 画像 | | 1枚（一覧と詳細の上部に出す） |
| ホスト | | 幹事・会場係の会員（複数）。会場での参加の承認（9-5）と、8章の役割を持つ |
| チェックインの受付時間 | | 初期値: 開始の60分前〜終了の60分後。名刺交換できる時間も同じ |
| 参加者一覧を見られる期間 | | 初期値: 終了から30日後まで（17章） |
| 状態 | ○ | 下書き／公開／終了／中止 |

- 「下書き」は管理者だけに見える。「公開」にすると、表示範囲の会員に見える。
- 「中止」にすると、名簿に結び付いた人に通知し、会場タグは使えなくなる。名刺交換QRも出せなくなる。
- 終了は終了時刻を過ぎたら自動で表示する（保存する状態は変えず、表示で判定する）。
- **申込・定員・キャンセル待ち・参加費は扱わない。** 申込の受け付けと参加費の管理はアプリの外で行い、その結果を参加者名簿（6-2）としてインポートする。

### 6-2. 参加者名簿のインポート

**インポートの流れ**（管理画面のイベントの参加者画面、14-1）
1. 管理者が、名簿のひな形（CSV）をダウンロードする。
2. 事務局の名簿から、ひな形の形で CSV を作り、アップロードする。Excel で保存した CSV（Shift_JIS）と UTF-8 のどちらも読めるようにする。
3. 取り込む前に、確認の画面を出す。行ごとに、アプリの会員との結び付けの結果（下の「結び付け」）と、読めなかった行（名前が空など）を示す。件数の要約（「120人 ― アプリ登録あり 45人・名前だけ一致 8人・アプリ未登録 67人」）を上に出す。
4. 「取り込む」で確定する。

**CSV の列**

| 列 | 必須 | 説明 |
|---|---|---|
| 名前 | ○ | 名簿に表示する名前 |
| ふりがな | | 並べ替えと、名前の検索に使う |
| 電話番号 | | アプリの会員との結び付けに使う。参加者には見せない |
| メールアドレス | | アプリの会員との結び付けに使う。参加者には見せない |
| 区分 | | 例:「会員」「来賓」「同伴」。名簿に表示する（任意の文字） |
| 管理用メモ | | 管理者とホストだけが見る |

**結び付け**（Cloud Functions で行う）
- 電話番号が、アプリの会員のログイン用の電話番号と一致した行は、その会員に結び付ける（アプリ登録あり）。
- 電話番号で一致しなければ、メールアドレスが、会員のログイン用のメールアドレスと一致した行を結び付ける。
- 名前だけが会員の表示名と一致した行は、結び付けない（同姓同名がありうるため）。「名前だけ一致」として、本人がチェックインのときに確かめる（9-3）か、管理者が確定する。
- どれにも当てはまらない行は「アプリ未登録」とする。
- 結び付けの対象は、そのイベントの所属のコミュニティの会員だけとする（ルートのイベントはルートの会員とゲスト、連携コミュニティのイベントはそのメンバー）。

**取り込み直し**
- 名簿は、イベントの前に何度でも取り込み直せる（申込の受け付けがアプリの外で続くため）。
- 取り込み直すと、同じ人の行は更新し、新しい行は加え、CSV から消えた行は名簿から外す。同じ人かどうかは、電話番号、メールアドレス、名前とふりがなの順で照らし合わせる。
- すでにチェックイン済みの行は、CSV から消えても外さない（確認の画面で知らせる）。結び付けとチェックインの記録は、取り込み直しても変えない。

**その他の編集**
- 管理画面で、1行ずつの追加・修正・削除と、結び付けの確定・解除ができる。
- 当日、ホストが会場で名簿に追加できる（9-6）。

**電話番号・メールアドレスの扱い**
- 結び付けのためだけに使う。参加者の名簿の画面には出さない。ルールで、管理者と Cloud Functions だけが読める場所に分けて置く（15・17章）。
- イベントの終了から30日後（`attendeeListUntil`）に、電話番号・メールアドレスを消す（名前・区分・チェックインの記録は残す）。

## 7. 会員の画面（イベント）

### 7-1. イベント一覧（`/events`、メイン機能「イベント」）

- 既存の仮画面を置き換える。
- 「これから」と「これまで」を切り替える。「これから」は開始日時の近い順、「これまで」は新しい順。
- 1件に表示するもの: 画像、所属のロゴと名称、タイトル、日時、会場名、自分の状態（名簿に載っています／チェックイン済み）。
- 所属で絞り込める（自分が所属するコミュニティの数が2つ以上のときだけ出す）。
- 当日（チェックインの受付時間中）のイベントは一番上に大きく出し、チェックイン済みなら「会場モードを開く」ボタンを出す。
- 自分が作った・参加したプライベートイベントも一覧に出す（「プライベート」の印を付ける）。交換できる時間中なら「名刺交換」ボタンを出す。
- 正規の会員には、一覧の上に「プライベートイベントを作る」ボタンを置く（5-4）。

### 7-2. イベント詳細（`/events/:eventId`）

- 6-1 の内容を表示する。申込のボタンは無い（申込はアプリの外で行う）。
- 自分が名簿に載っていれば「参加者名簿に載っています」と表示する。載っていなければ、「参加の申込は、事務局にお問い合わせください」と表示する（問い合わせ先は説明に書く）。
- **参加者一覧**（7-4）へのボタンを出す（自分が名簿に結び付いているときだけ）。
- **参加予定の人**（8-2）: 自分が名簿に結び付いていれば、「参加予定の人に自分を見せる」に同意した他のアプリ登録ありの人を、共通点の多い順に見られる。ここから「会いたい」（8-2）を送れる。
- 当日は「チェックイン」ボタン（会場タグを読み取る画面へ。9-3）と、チェックイン済みなら「会場モード」ボタンを出す。
- 「これまで」のイベントで出席した場合は、「この日に会った人」（F3 のつながり一覧をこのイベントで絞り込んだもの）へのリンクを出す。
- プライベートイベントの詳細は 5-4 の「見える人」のとおり。

### 7-3. 会場モード（`/events/:eventId/live`）

チェックインした人だけが開ける。大きな文字・大きな写真で、懇親会の場で片手で使える作りにする。

- **いま会場にいる人**: チェックイン済みの人を写真付きで一覧する（`hideFromList` の人は出さない）。並びは「自分との共通点が多い順」を初期値とし、「名前順」に切り替えられる。各人に、声かけ歓迎・ホストの印（8-3・8-4）と、話のきっかけ（8-5）を表示する。
- **共通点のお知らせ**: 画面上部に「あなたと同じ高校の人が5人、同じ部活の人が2人、同じ市町村の出身の人が7人います」のように表示する。タップするとその人たちに絞り込む。
  - 共通点は、テナントのプロフィール項目のうち、本人が公開している項目どうしで判定する（相手が非公開にしている項目は使わない）。判定はクライアント側で行う。
- **同じテーブルの人**: テーブルの会場タグでチェックインした（またはテーブルを移った）とき、そのテーブルの人を一覧の先頭に分けて表示する。
- **テーブルの見え方**: 他の人がどのテーブルにいるかは、一般の参加者には見せない（自分と同じテーブルかどうかだけ分かる）。居場所が分かるのは、「会いたい」が成立した相手（8-2）、話し相手の募集に応じた人（8-3）、ホスト（8-4）だけとする。管理者は参加者画面で全員のテーブルを見られる。
- 各人の行には「つながっています」の印か、「名刺交換」ボタン（F1 の名刺交換画面を、このイベントを選んだ状態で開く。自分も相手もゲストでないときだけ）と「申し込む」ボタン（コネクト申請。`canDiscover` を満たすときだけ）を出す。
- 「一覧に自分を表示しない」の切り替え（`hideFromList`）を画面の下に置く。
- 会場モードを開いている間に名刺交換（F1）・名刺QR（F4）でつながった場合は、出会いの記録にこのイベントを自動で付ける（10-8）。
- ホストの会場モードには「受付」タブを置く。会場での参加の承認（9-5）、名簿の検索と代理のチェックイン・名簿への追加（9-6）を行う。

### 7-4. 参加者一覧（`/events/:eventId/attendees`）

- 名簿に結び付いた人（アプリ登録あり）が見られる。イベントの前から、参加者一覧を見られる期間（終了から30日後まで、`attendeeListUntil`）まで見られる。
- 名簿の全員を、ふりがな（無ければ名前）の順に一覧する。1行に表示するもの:
  - 名前と区分
  - 状態の印: **チェックイン済み**（当日）／**アプリ登録あり**／**アプリ未登録**
  - アプリ登録ありの人は、プロフィール写真と、タップでプロフィール（公開範囲は既存の設定に従う）。つながっていれば「つながっています」の印
- 上部に人数の要約を出す:「参加予定 120人（アプリ登録あり 45人）― いま会場に 38人」。
- 状態（チェックイン済み／アプリ登録あり／アプリ未登録）と、名前の文字で絞り込める。
- アプリ登録ありで `hideFromList` をオンにしている人は、名前・区分・状態だけを出し、写真とプロフィールは出さない。
- 当日は、チェックインの状態をリアルタイムで更新する。
- アプリ未登録の人の名前を参加者に見せるのは、紙の参加者名簿を配るのと同じ扱いとする（22章 要決定事項）。
## 8. 会場で若手を孤立させない機能

### 8-1. 狙いと考え方

- 年上の参加者が多い懇親会では、若手、特に知り合いのいない人や自分から話しかけるのが苦手な人は孤立しやすい。孤立した経験は、次のイベントに来ない理由になる。
- 打ち手の方向は、**若手に「話しかけさせる」のではなく、「話しかけてもらえる」状態をつくること**とする。場慣れした年上の参加者・ホストのほうが、声をかけるのは得意である。
- 4つの機能で構成する。

| ID | 機能 | 若手にとって | 年上の参加者・ホストにとって |
|---|---|---|---|
| A | 会いたい | 事前に「会いたい」と伝えておけば、相手が探しに来てくれる | 後輩から指名される。会場で相手がどこにいるか分かる |
| B | 話し相手の募集と声かけ歓迎 | 一人のとき、目立たずに助けを呼べる | 「声かけ歓迎」の印で、話しかけてよい先輩として見つけてもらえる。困っている若手のところへ行ける |
| C | ご紹介 | ホストが引き合わせてくれる | 誰と誰を引き合わせるとよいか、アプリが提案する |
| D | 話のきっかけ | 相手との共通点と話題が分かる | 同じ |

- これらは LINE などのオンラインの連絡手段には無い、**リアルの場で出会いを生む機能**であり、このサービスの中心的な価値と位置づける。
- イベントごとに、管理者が A・B・C を個別にオン・オフできる（初期値: すべてオン）。D は常に使える。

**共通の前提**
- **若手**: テナントの設定「若手とみなす年代」（初期値: 30代まで）に当てはまる人。年代はプロフィールの自動計算の「年代」を使い、本人が非公開にしていれば使わない。
- **初参加**: そのテナントのイベントに、これまでに出席したことが無い人。チェックイン時に判定して参加者の記録に持つ（`isFirstTime`）。
- 若手・初参加の印は、本人と、声かけ歓迎・ホストの人だけに見える（一般の参加者の一覧には出さない）。
- 共通点・話題の判定に使うのは、相手が公開している項目だけとする。
- 監視の仕組みは作らない（「誰とも話していない人」を自動で検知するなどはしない）。助けを求めるのは本人の操作だけとする。

**共通点に使う項目の対応づけ（テナントの設定）**
- プロフィール項目はテナントごとに違うため、管理画面の「プロフィール項目」に、次の役割を項目に割り当てる設定を加える（`matchingFields`）。
  - 学校（例: 出身高校）、部活動、卒業年（期の差の計算に使う）、出身地、年代、話せること
- 東京岐阜県人会では、**「高校の卒業年」と「話せること」の項目が今は無い**ため、追加が必要（22章 要決定事項）。
  - 卒業年: 入力方法「選択式」で年を選ぶ。期の差（「20期上の先輩」）の計算に使う。
  - 話せること: 入力方法「複数入力」。例:「就活の相談」「金融業界」「起業」「岐阜へのUターン」「子育て」。会員検索の条件にも使える。

### 8-2. A: 会いたい

**事前（名簿に載ってから当日まで）**
- 名簿に結び付いた人は、イベント詳細で「参加予定の人に自分を見せる」を選べる（`showInPreview`、初期値: オン）。オフの人は、参加予定の人の一覧に出ない。
- イベント詳細の「参加予定の人」に、自分と共通点のある人を共通点の多い順に出す。上部に「あなたと同じ高校の先輩が3人参加予定です」のように要約する。
- 各人に「会いたい」ボタンを置く。押すと、送る理由を選ぶ（任意）:「同じ高校の先輩なので」「仕事の話を聞きたい」「就活の相談をしたい」「同じ地元なので」「その他（30文字まで）」。
- 相手に通知が届く:「若手の○○さん（○○高校 2018年卒）が、懇親会であなたに会いたいと言っています」。相手は「会いましょう」か「今回は見送る」を選ぶ。
  - **送った側には、見送られたことを伝えない。** 送った側の表示は「届けました」のまま変わらず、成立したときだけ「○○さんも会いたいそうです」と知らせる。断られる不安で送るのをためらわないようにするため。
- 誰でも誰にでも送れる（年齢で制限しない）。ゲストも送れる（コネクト申請ではないため。会場で出会うための機能に限る）。

**当日**
- 成立した二人がどちらもチェックインしたら、両者に通知する:「○○さんが会場に来ました。テーブル5にいます」。相手がテーブルを移ったら、居場所を更新する。
- 会場モードの上部に「会う約束」として成立した相手を並べ、写真と今いるテーブルを出す。会ったら「会えました」を押す（出会いの記録に残り、名刺交換を案内する）。
- 当日の会場モードからも「会いたい」を送れる。

**上限と受け付けの設定**
- 1人が1つのイベントで送れるのは5件まで。
- 受け取る側は、承諾待ちが10件を超えたら新しい「会いたい」を受け付けない（送る側には「届けました」と表示し、受け取る側への通知はまとめて1回にする）。
- イベント詳細・会場モードで「会いたいを受け付けない」を選べる（`meetRequestsEnabled`）。オフの人には「会いたい」ボタンを出さない。

### 8-3. B: 話し相手の募集と声かけ歓迎

**声かけ歓迎の印**
- イベント詳細・チェックイン後に「若手や初めての方に声をかけます」を選べる（`welcome`）。選んだ人には、会場モードの一覧で「声かけ歓迎」の印が付く。
- 若手・初参加の人の会場モードでは、声かけ歓迎の人を一覧の先頭近くに出す（共通点の多い順の中で優先する）。
- 声かけ歓迎の人の会場モードには、「今日、初めて参加した若手」が分かるように印を出す。

**話し相手の募集**
- 会場モードの下に、控えめなボタン「話し相手を探しています」を置く。周りの人に見えても目立たない文言・見た目にする。
- 押すと、今いる場所を確かめる（テーブルでチェックインしていればそのテーブル。違えば選び直せる。「受付付近」「その他（10文字）」も選べる）。一言を添えられる（任意。例:「就活中です」）。
- 知らせが届く相手: そのイベントの**ホスト**（8-4）と**声かけ歓迎**の人。同じテーブルの人を優先し、最初は近いテーブル（番号の近い順）の歓迎の人と全員のホストに送る。
  - 通知の文:「テーブル4の△△さん（初参加・20代・○○高校）が話し相手を探しています」と、本人の写真。
- 最初に「行きます」を押した人が引き受ける。他の人の通知は「□□さんが向かっています」に変わる。
- 募集した本人には「□□さん（写真）が向かっています」と表示する。顔が分かるようにするため。
- 5分たっても誰も引き受けなければ、ホスト全員にもう一度通知する（`escalatedAt`）。それでも無ければ、本人に「いま手が空いている人がいないようです。受付にお声がけください」と表示する。
- 本人はいつでも取り下げられる。会えたら、本人か引き受けた人が「会えました」を押す。
- 募集は1人1件まで。終わってから10分は次の募集をできない（いたずら防止）。
- 募集していることは、一般の参加者の一覧には出さない。

### 8-4. C: ご紹介（ホストによる引き合わせ）

**ホスト**
- 管理者が、イベントごとにホスト（幹事・会場係）を会員から選ぶ（`hosts`）。ホストは会場モードで「ホスト」の印が付き、話し相手の募集の通知を受け、ご紹介の提案を見られる。
- ホストは全員のテーブルを見られる（引き合わせるため）。

**紹介の提案**
- ホストの会場モードに「ご紹介」タブを置く。チェックイン済みの人から、引き合わせるとよい2人の組み合わせを、優先度の高い順に出す。
- 1件の表示:「A さん（初参加・20代・テーブル3）と B さん（声かけ歓迎・60代・テーブル7）― 同じ○○高校サッカー部、32期違い。B さんの話せること: 金融業界」
- 提案の優先度（Cloud Functions で計算する）:
  - 一方が若手または初参加で、もう一方が声かけ歓迎かホストである組み合わせを優先する。
  - 共通点の重み: 同じ学校かつ同じ部活 ＞ 同じ学校 ＞ 同じ部活 ＞ 同じ出身地 ＞ 若手の話したいこと（8-5）と先輩の話せることの一致。
  - 期の差・年代の差が大きい組み合わせ（縦のつながり）を少し優先する。
  - すでにつながっている組み合わせ、「会いたい」が成立している組み合わせ、どちらかが一覧に出ない設定（`hideFromList`）の人は除く。
  - その日すでに紹介された人は順位を下げる（同じ人に紹介が集中しないため）。
- 操作:「紹介しました」「今回は見送る」。「紹介しました」を押すと、2人に「□□さんの紹介で、○○さんと知り合いました」と通知し、出会いの記録の場面ラベルに「□□さんの紹介」を加える。
- 声かけ歓迎の人の会場モードにも「あなたに紹介したい方」として、自分を含む提案を3件まで出す（自分から声をかけに行けるように）。

### 8-5. D: 話のきっかけ

- 会場モードの一覧と、相手の詳細に表示する。
- **共通点の要約**: 「同じ○○高校・サッカー部（32期上）・同じ岐阜市の出身」。期の差は、卒業年の項目が両者にあるときだけ出す。
- **話せること**: 相手のプロフィールの「話せること」。
- **今日話したいこと**: チェックイン後に任意で一言（30文字まで）を設定できる（`talkTopic`。例:「就活中です」「岐阜の地酒の話をしたい」）。その日のイベントの中だけで表示する。
- **話しかけるひと言の例**: 共通点から、テンプレートで1〜2文を出す（AI は使わない）。
  - 同じ学校:「○○高校の何年卒ですか？ 私は2018年卒です」
  - 同じ部活:「サッカー部だったんですね。当時の顧問の先生は…」
  - 同じ出身地:「岐阜市のどのあたりのご出身ですか？」
  - 話せることと話したいことが一致:「金融業界のお話を伺ってもいいですか？」
  - テンプレートは `src/app/core/utils/` に置き、既存の例文（message-templates）と同じく、テナントごとに差し替えられる作りにする。

### 8-6. 通知の届け方

- 会場では即時性が大事なため、会場モードを開いている間は Firestore のリアルタイムの監視で、画面上部のお知らせとして出す（音とバイブレーションは端末の設定に従う）。
- 会場モードを閉じているときは Web Push で届ける。iPhone ではホーム画面に追加したアプリで通知を許可している場合だけ届くため、チェックイン時に通知の許可を案内する。
- 通知の種類は16章にまとめる。

## 9. 会場タグとチェックイン

### 9-1. 会場タグ

- 会場タグは**コミュニティ（ルート・連携コミュニティ）ごとに持つ、使い回せる物理的な札**とする。イベントごとに作り直さない（NFC シールを毎回貼り替えないため）。
- 種類:
  - **受付**: チェックインする。
  - **テーブル**: チェックインし（まだなら）、そのテーブルに座ったことを記録する。テーブル番号（または名前、例:「3」「来賓席」）を持つ。
- URL: `https://{テナントのドメイン}/e/{タグコード}`（タグコードは推測されにくい英数字10文字。紛らわしい文字は除く。名刺コード（13-3）と同じ作り方）
- 1枚の札に、NFC タグ（URL を書き込む）と、同じ URL のQRコードを印刷する。iPhone・Android のどちらも、かざすかQRを読めば同じ URL が開く。
- タップされたとき、サーバーは**そのコミュニティのイベントのうち、チェックインの受付時間中で、そのタグを使うことになっているもの**を探す（9-3）。
  - イベントの作成時、初期値ではそのコミュニティの有効な会場タグをすべて使う。イベントごとに使うテーブルを選び直せる（会場によってテーブル数が違うため）。
  - 同じ会場タグを、受付時間が重なる2つのイベントに割り当てることはできない（保存時に確かめる）。

### 9-2. 会場タグの準備（管理画面、14-2）

1. 管理者が「会場タグ」画面で、受付タグ（1枚以上）とテーブルタグ（枚数を指定。番号は1から連番）をまとめて作る。
2. **札の印刷**: 札の PDF をダウンロードする（14-2）。
3. **NFC への書き込み**:
   - Android の Chrome では、管理画面から直接書き込める（Web NFC の `NDEFReader.write`）。画面の指示に従い、札の NFC シールに1枚ずつスマホをかざす。書き込み後、読み返して URL が正しいか確かめる。
   - iPhone ではブラウザから書き込めないため、管理画面に表示する URL を、市販の NFC 書き込みアプリで書き込む手順を案内する。
   - 推奨する NFC シール: NTAG213 以上（URL は40文字程度で収まる）。
   - **書き込んだら、ロック（書き換え禁止）を推奨する。** ロックしないと、第三者が別の URL（偽サイトなど）に書き換えられるため。管理画面の書き込み機能では「書き込み後にロックする」をオンを初期値にする（Web NFC の `makeReadOnly`。非対応なら案内のみ）。
4. 札をなくした・壊れた・いたずらされたときは、その会場タグを「使えなくする」にして、新しい会場タグを作り、札を作り直す。

### 9-3. チェックインの流れ（会員）

**読み取りの入口**
- **札にスマホをかざす／カメラアプリでQRを読む**: ブラウザで `/e/{タグコード}` が開く。
  - ログインしていなければ、主催のコミュニティ名・ロゴと、2つのボタンを出す（`getVenueTagPreview`）。
    - 「アプリを使っている方（ログイン）」… ログイン画面へ。パスキーを使っていれば、顔認証などですぐにログインできる（パスキーは端末のブラウザとホーム画面のアプリで共有される）。ログイン後に `/e/{タグコード}` に戻ってチェックインする。
    - 「はじめての方（アプリを使っていない）」… 会場での参加の申し込みへ（9-5）。
- **アプリ内で読む**: イベント詳細の「チェックイン」ボタン、または名刺交換の「相手のQRを読み取る」（10-1）で札のQRを読む。Android では、同じ画面で NFC の読み取り（Web NFC の `NDEFReader.scan`）も待ち受ける。iPhone のホーム画面のアプリでは NFC を読めないため、QR を読むか、ブラウザからかざす。
- **名刺交換QRを読む**: チェックイン済みの人の名刺交換QRを読み取ると、その場でチェックインされる（10-4 の6.）。

**処理**（Cloud Functions `checkIn({ tagCode })`）
1. タグコードから会場タグ（テナント・所属・種類・テーブル）を解決する。使えなくなったタグは「この札は使えなくなっています。受付にお声がけください」。
2. そのタグを使う、チェックインの受付時間中のイベントを探す。無ければ「いま受付中のイベントはありません」と、そのコミュニティの次のイベント（見える人にだけ）を表示する。
3. 読んだ人がそのイベントを見られるか（5-2・5-3）を確かめる。見られなければ 9-4。
4. 名簿から読んだ人の行を探す（**名前を確かめて自動でチェックイン**）:
   - **名簿に結び付いている**: 確認なしでチェックインし、「○○さん、ようこそ」と名簿の名前を大きく出す。名前が違うときのために「お名前が違う場合は、受付にお声がけください」を小さく添える。
   - **名前だけ一致の行がある**（6-2）: 「名簿の『○○（ふりがな）』さんは、あなたですか？」と名前と区分を出す。「はい」で行を自分に結び付け（`linkedVia: 'self'`）、チェックインする。「いいえ」なら、次の「名簿に見つからない」と同じにする。候補が2行以上なら、区分を添えて選んでもらう。
   - **名簿に見つからない**: 「参加者名簿にお名前が見つかりません。受付にお声がけください」と表示し、何も記録しない。受付では、ホストが名簿の行を探して結び付けるか、名簿に追加してチェックインする（9-6）。
   - **すでにチェックイン済み**: チェックインの時刻は変えない。
5. チェックインの記録を書く（15章）。名簿の行に checkedInAt・checkedInVia を付け、会員の参加者の記録（`participants/{memberId}`）を作る・更新する。
   - テーブルタグなら、今いるテーブル（`seats/{memberId}` の `currentTable`）を更新し、テーブルの履歴に加える。会う約束の相手がいれば、新しい居場所を知らせる。
   - 初めてのチェックインなら、これまでの出席の有無から `isFirstTime` を決める。
6. 結果の画面: 「チェックインしました」（テーブルタグなら「テーブル3に着きました」）と、会場モードへの大きなボタン。2回目以降のタップ（テーブルの移動など）では、確認なしで会場モードを開く。

- 同じ人の `checkIn` は1分に10回までとする。
- 名簿に結び付けられるのは、1つの行に1人だけ。すでに別の会員に結び付いた行は、本人の確認（4. の「はい」）では選べない（ホスト・管理者が付け替える）。

### 9-4. 見られないイベントのタグを読んだとき

- イベントのタイトルや参加者は表示しない。
- 「このイベントは、主催のコミュニティのメンバーだけが参加できます」と、主催のコミュニティの名称を表示する。
- 連携コミュニティのイベントで、読んだ人がそのメンバーでない場合は、「受付にお声がけください」と案内する（ホストが名簿を確かめ、既存の連携コミュニティへの参加を案内する）。

### 9-5. アプリ未登録の人の参加（会場での参加の申し込みとホストの承認）

名簿に載っていてアプリを使っていない人が、会場でその場でアプリに登録し、チェックインする。会場タグだけでは誰でも登録できてしまうため、**イベントのホストが承認する**。名簿に載っていることと、ホストがその場で本人を確かめることが、既存の招待の代わりになる。

**参加する人の操作**（`/e/{タグコード}` の「はじめての方」から）
1. 名簿から自分の名前を探して選ぶ（ふりがな・名前で検索する。アプリ未登録・名前だけ一致の行だけを出す）。名簿に無ければ「受付にお声がけください」と表示する。
2. 電話番号を入れ、SMS の認証コードで確かめる（既存の参加の流れと同じ仕組み）。
3. ログインID を決める（既存の参加の流れと同じ）。
4. 「ホストの承認を待っています。近くのホストか受付にお声がけください」と表示し、承認を待つ。待っている間、画面に自分の名前と、確認のための4桁の番号（申し込みごとに作る）を大きく出す。
5. 承認されたら、画面が自動で切り替わり、ログインした状態で「チェックインしました」になる。会場モードへの大きなボタンと、ホーム画面への追加（通知を受け取るため）の案内を出す。
- 断られたときは「受付にお声がけください」と表示する。30分たっても承認されなければ、申し込みは取り消しになり、もう一度申し込める。

**ホストの操作**（会場モードの「受付」タブ）
- 承認を待っている申し込みを一覧する。1件に表示するもの: 選んだ名簿の名前・区分・管理用メモ、確認の4桁の番号、電話番号の下4桁、申し込んだ時刻。
- 本人と顔を合わせて、名前と4桁の番号を確かめ、「承認」か「お断り」を押す。
- 申し込みがあると、そのイベントのホスト全員に通知する（16章）。誰か1人が承認すれば決まる（先に押した人の操作だけが通る）。ほかのホストの一覧からは消える。

**承認したときの処理**（Cloud Functions `approveEventJoin`）
- アカウントを作る。区分は既存の招待による参加と同じにする（ルートのイベントならゲスト、連携コミュニティのイベントならその連携コミュニティのメンバー）。正規の会員への切り替えは、既存の会員登録の申請で行う。
- 名簿の行をその会員に結び付け（`linkedVia: 'invite'`）、チェックインする（`checkedInVia: 'invite'`）。
- 招待の記録（`invites`）に、承認したホストを招待した人として残す（`via: 'event'`）。承認したホストとのつながりとトークは作らない（ホストに承認が集まるため）。
- 承認したホストと承認の時刻を、申し込みの記録に残す。
- 参加する人の端末は、申し込みのときに受け取った合言葉（申し込みごとのランダムな文字列）で、承認の結果とログインのためのトークンを受け取る（`completeEventJoin`）。

**乱用への対策**
- 申し込めるのは、そのイベントのチェックインの受付時間中だけ。
- 選べるのは名簿のアプリ未登録・名前だけ一致の行だけ。1つの行に、承認を待つ申し込みは1件だけ。
- 同じ電話番号からの申し込みは、1つのイベントで3回まで。
- すでにアプリの会員である電話番号で申し込んだときは、「この電話番号はアプリに登録されています。ログインしてください」と案内し、申し込みを作らない。

### 9-6. ホスト・管理者によるチェックインと名簿への追加

- スマホを持っていない・操作できない人のため、ホスト（会場モードの「受付」タブ）と管理者（参加者画面、14-1）が、名簿の行の「チェックイン」ボタンで代わりにチェックインできる（`checkedInVia: 'host'` / `'admin'`）。アプリ未登録の人もチェックインの記録だけは付けられる（出席簿のため）。
- 名簿に見つからない人が来たときは、ホストがその場で名簿に追加し（`source: 'onsite'`）、チェックインできる。その人がアプリを使っていれば、会員を検索して結び付ける。使っていなければ、続けて 9-5 の申し込みをしてもらう。
- ホストは、名簿の行の結び付けを確定・付け替えできる（名前だけ一致の行、取り違えの訂正）。

### 9-7. 会場にいない人のチェックインへの対策

- 札の URL は写真に撮られて広まりうる。そのため次で抑える。
  - チェックインはイベントの受付時間中だけ。
  - チェックインできるのは、名簿に結び付いた（または本人が名前を確かめた）ログイン済みの会員だけ。アプリ未登録の人は、ホストの承認が必要。
  - ホスト・管理者は不審なチェックインと結び付けを取り消せる。
- 位置情報による確認は、利用者の負担とプライバシーの観点から行わない（Phase 1）。

## 10. F1: QRで名刺交換

### 10-1. 画面（`/connect/exchange`、ナビ: つながる > 名刺交換）

- 「つながる」のタブの先頭に「名刺交換」を加える（既存の「招待」より前）。ゲストにはこのタブを出さない。
- **使える人**: 正規の会員（`member`。区分なしの昔からの会員を含む）と、連携コミュニティだけのメンバー（`community`）。ゲスト（`guest`）は使えない。
- **今日のイベント**: 画面上部で、名刺交換をするイベントを選ぶ。選べるのは、交換できる時間の中にあり、自分が次に当てはまるイベント。
  - 公式のイベント: そのイベントにチェックイン済み（9-3）
  - プライベートイベント: 自分が作った、または参加者になっている（5-4）
  - 候補が1つなら自動で選ぶ。2つ以上なら、開始時刻の近いものを初期値にする。会場モード（7-3）から開いたときは、そのイベントに固定する。
  - 候補が無いとき:「名刺交換は、イベントの中で使えます」と表示し、次を出す。
    - 公式のイベントが受付時間中なら、「チェックインする」（会場タグの読み取りへ）
    - 正規の会員には、「プライベートイベントを作る」（5-4。作ったらこの画面に戻り、そのイベントを選ぶ）
- 招待先（名刺交換QRの `code`）は、イベントの所属から決まる。ルートのイベントならルートの招待コード、連携コミュニティのイベントならその連携コミュニティの招待コード。`InviteTargetPicker` は使わない。
- 画面は2つの切り替え（大きなボタン）で構成する。
  - **「自分のQRを見せる」**（初期表示）… イベントが選ばれているときだけ使える。
  - **「相手のQRを読み取る」** … イベントを選んでいなくても使える。プライベートイベントには、作成者などのQRを読み取ることで参加するため（10-4）。イベントを選んでいないときは、読み取りを初期表示にする。

**自分のQRを見せる**
- 名刺交換QRを大きく（画面幅いっぱい、最低 280px 四方）表示する。中心に招待先のロゴを重ねる（既存と同じく誤り訂正 H）。
- QRの下に、自分の写真・名前・イベントのタイトル・「このQRを相手に読み取ってもらってください」を表示する。
- トークンは**60秒ごとに自動で更新**する（10-3）。更新は画面に何も出さず、QRだけを差し替える。
- 画面を表示している間は、Screen Wake Lock API で画面が消えないようにする（非対応の端末では何もしない）。
- 相手が読み取ってつながったら、見せている側にもその場で知らせる（Firestore の自分の `encounters` を監視し、新しい記録ができたら「○○さんとつながりました」と写真付きでトースト表示する）。

**相手のQRを読み取る**
- アプリ内でカメラを起動して読み取る（`getUserMedia`）。
- 読み取りには `BarcodeDetector` が使える端末ではそれを使い、使えない端末（iOS Safari など）ではライブラリ（`jsqr` を想定）で読む。
- **アプリ内の読み取りを用意する理由**: iPhone では、ホーム画面に追加したアプリと Safari でログイン状態が別になる。カメラアプリで読み取ると Safari が開き、ログインからやり直しになる。懇親会の場でそれは使いものにならない。
- カメラの許可が得られないときは「設定でカメラを許可してください」と案内し、あわせて「相手のカメラで自分のQRを読み取ってもらう」方法を案内する。
- 名刺QR（`/c/{名刺コード}`）も読み取れるようにする。その場合は F4 の処理（13-4）を行い、選んでいるイベントを渡す。
- 会場タグ（`/e/{タグコード}`）も読み取れるようにする。その場合はチェックイン（9-3）を行う。
- 読み取った URL が自分のテナントの `/join?code=…`・`/c/…`・`/e/…` の形でなければ、「TOKYO GIFU CONNECT のQRコードではありません」と表示する（ブランド名はテナントのものを使う）。
- 読み取る側のイベントは、見せている側のトークンで決まる（10-4）。読み取る側がどのイベントを選んでいるかは使わない。
- 読み取ったら確認なしで処理を始める（10-4）。結果は 10-5 の画面で出す。

### 10-2. QRコードの中身

- URL: `https://{テナントのドメイン}/join?code={招待コード}&x={交換トークン}`
  - `code` は既存の招待QRのコード（招待先ごとに1つ。`getMyInviteQr` と同じものを使う）。
  - `x` は交換トークン（10-3）。
- **アカウントのない人**がカメラアプリで読み取っても、既存の参加の流れ（ゲストとして参加）がそのまま動く。名刺交換QRは招待QRとしても働く。
- `x` が無い URL（招待QRを撮影したものなど）を会員が読み取った場合は 10-4 の「申請に切り替え」の扱いになる。紙の名刺に印刷するときは、招待QRではなく名刺QR（F4）を使う。

### 10-3. 交換トークン

- Cloud Functions `createExchangeToken({ eventId })` で発行する。
  - 呼べる人: ゲスト以外で、そのイベントで名刺交換できる人（10-1 の「今日のイベント」の条件。公式のイベントはチェックイン済み、プライベートイベントは作成者か参加者）。
  - イベントが中止されていない、交換できる時間の中であることを確かめる。外れていれば「このイベントの名刺交換の時間は終わりました」。
  - 招待コード（inviteCode）は、イベントの所属から決める（ルートのイベントはルート、連携コミュニティのイベントはその連携コミュニティあての、自分の招待コード。`getMyInviteQr` と同じものを使う）。
  - 推測されない32文字以上のランダム文字列にする。
  - 保存: `exchangeTokens/{token}` に tenantId、memberId（見せている人）、inviteCode、communityId?、eventId、createdAt、expiresAt を持つ。
- **有効期間**:
  - 会員どうしのその場のつながり（10-4）: 発行から**5分**。
  - アカウントのない人の参加（10-6）: 発行から**30分**。SMS の認証などに時間がかかるため。出会いの記録にだけ使う。
- クライアントは60秒ごとに発行し直す。1人あたりの発行回数は 1分に3回・1時間に120回までとする（超えたら更新を止め、最後のQRを出し続ける）。
- 期限切れのトークンは、スケジュール関数で1日1回削除する（または Firestore の TTL ポリシーを `expiresAt` に設定する）。
- `exchangeTokens` はクライアントから読み書きできない（ルールで全面禁止。`inviteCodes` と同じ扱い）。

### 10-4. 読み取ったときの処理（会員どうし）

Cloud Functions `exchangeConnect({ code, token? })`。

1. 読み取った人（以下「読取者」）がログインしていて、`phoneIndex` から会員であることを確かめる。
2. **読取者がゲストなら、何もせずに案内する**:「名刺交換は、会員登録が済むと使えます」と、マイページの会員登録へのボタン。出会いの記録も作らない。
3. `code` から見せている人（以下「提示者」）とテナントを解決する（既存の `resolveInvitation` を使う）。
4. 次の場合はエラーにする。
   - 読取者と提示者のテナントが違う →「別のコミュニティのQRコードです」
   - 読取者＝提示者 →「ご自身のQRコードです」
   - どちらかが停止中（`isActive: false`）
5. **トークンの確認**: `token` があり、`exchangeTokens/{token}` の memberId が提示者で、発行から5分以内であれば「その場の同意あり」とし、トークンの eventId をこの交換のイベントとする。イベントが中止された・交換できる時間を過ぎたときは、トークンが無いものとして扱う。
6. **同意があるとき — 読取者をイベントに加える**（5-2・5-4）:
   - **ルートのイベント**: 読取者が正規の会員でなければ（連携コミュニティだけのメンバー）、「このイベントは、県人会の会員だけが参加できます」と表示し、何も作らない。
   - **連携コミュニティのイベント**: 読取者がその連携コミュニティのメンバーでなければ、既存の `joinCommunityWithExistingAccount` の流れ（規約の同意・承認の要否を含む）を先に案内する（`needsCommunityJoin`）。参加が済んだら、クライアントは同じ `code`・`token` でもう一度呼ぶ。そのときトークンが期限切れなら、8. の申請に切り替える。
   - **公式のイベント**: 読取者がチェックイン済みでなければ、その場でチェックインする（`checkedInVia: 'exchange'`）。名簿の探し方は 9-3 の4. と同じ。名簿に結び付いていればそのままチェックインする。名前だけ一致の行があれば `needsRosterConfirm` を返し、クライアントは名前の確認（「名簿の『○○』さんは、あなたですか？」）をしてから、同じ `code`・`token` と確認した行でもう一度呼ぶ。名簿に見つからなければ「参加者名簿にお名前が見つかりません。受付にお声がけください」と表示し、何も作らない。提示者がチェックイン済みであることが、会場にいる確認の代わりになる。
   - **プライベートイベント**: 読取者が参加者でなければ、参加者に加える（`joinedVia: 'exchange'`、`invitedBy`: 提示者）。参加者の上限（5-4）に達していれば「このイベントの参加者は上限に達しています」と表示し、何も作らない。
7. 同意があるときのつながり:
   - 両者が同じイベントの参加者で、どちらもゲストでないので、`canDiscover` は使わない（ルートのイベントなら両者ともルートの会員、連携コミュニティのイベントなら両者ともその連携コミュニティのメンバーであり、つながれる範囲に入る）。
   - すでにつながり（accepted）があれば、つながりは作らず、出会いの記録だけを更新する。
   - つながりが pending（どちらかが申請中）なら、accepted に更新する。
   - つながりが無い、または declined なら、accepted で作る（`source: 'qr'`）。
   - いずれも、1対1のルームが無ければ作る（既存の `connectWithInviter` の処理を共通の関数に切り出して使う。`requestedBy` は提示者にする）。
   - 両者の出会いの記録（11章）を作る・更新する。`via: 'qr-exchange'`。`eventIds` にイベントを加え、場面ラベルにイベントのタイトルを加える。
8. トークンが無い・期限切れ・提示者が一致しないとき（**申請に切り替え**。イベントの外の扱い）:
   - `canDiscover(読取者, 提示者)` が false なら、「この方とは、県人会のイベントで名刺交換するとつながれます」と表示し、何も作らない。
   - つながっていなければ、既存の `sendConnectionRequest` と同じ処理で、読取者から提示者へのコネクト申請（pending、`source: 'qr'`）を作る。
   - 読取者側だけに出会いの記録を作る（`via: 'qr-request'`。イベントは付けない）。提示者側の記録は、提示者が申請を承認したときに作る（`respondToConnectionRequest` に追記）。
9. 結果を返す: `{ result: 'connected' | 'alreadyConnected' | 'requested' | 'needsCommunityJoin' | 'needsRosterConfirm' | 'blocked', partner: { memberId, displayName, photoUrl }, event?: { eventId, title }, message? }`（`blocked` は 2.・6.・8. で何も作らなかったとき。`message` に案内の文を入れる）

- イベントへの追加（チェックイン・参加者の追加）、つながりの作成・更新、ルームの作成、出会いの記録は1つのトランザクション（またはバッチ）で行う。
- プッシュ通知: 提示者に「○○さんと名刺交換しました」を送る（16章）。申請に切り替えた場合は、既存の「コネクト申請の受信」の通知を送る。

### 10-5. 読み取った後の画面

- `connected` / `alreadyConnected`: 相手の写真（大きく）と名前、イベントのタイトル、「つながりました」（または「すでにつながっています」）を表示する。その下に次を置く。
  - 「メモ」入力欄（任意。例:「○○高校 昭和58年卒、ゴルフ好き」）。入力すると出会いの記録の note に保存する。
  - 「トークを開く」ボタン
  - 「続けて読み取る」ボタン（大きく。懇親会で何人とも交換するため、カメラにすぐ戻れること）
- `requested`: 「○○さんにつながりを申し込みました。承認されるとトークができます」と表示し、メモ欄と「続けて読み取る」を置く。
- `needsCommunityJoin`: 連携コミュニティへの参加の確認画面（既存）へ移る。参加が済んだら、名刺交換の処理を続ける（10-4 の6.）。
- `needsRosterConfirm`: 名簿の名前の確認を出す。「はい」で、名刺交換の処理を続ける（10-4 の6.）。
- `blocked`: `message` の案内と、案内に応じたボタン（会員登録など）、「続けて読み取る」を置く。
- 読み取ってプライベートイベントに加わったときは、名刺交換の画面の「今日のイベント」をそのイベントにする。続けて自分のQRを見せられる。

### 10-6. アカウントのない人が読み取ったとき

- 既存の参加の流れ（`/join?code=…` → 電話番号の確認 → 名前とログインID → ゲストとして参加）をそのまま使う。
- 参加が終わったら、`x` のトークンが発行から30分以内であれば、提示者との出会いの記録を両者に作る（`via: 'qr-exchange'`、`eventIds` にトークンのイベント、場面ラベルにイベントのタイトル）。つながりとトークは既存の `connectWithInviter` で作られる（招待による参加の扱い。名刺交換の機能を使ったことにはならない）。
- 参加した人はゲスト（ルートへの招待のとき）なので、イベントの参加者には加えない。その人が公式のイベントの名簿に載っていれば、会場タグでチェックインできる（9-3。名簿は名前だけ一致になるので、名前を確かめる）。連携コミュニティへの招待で参加した人（連携コミュニティのメンバー）は、そのイベントが連携コミュニティの公式のイベントなら、会場タグでチェックインすれば名刺交換を使える。
- `joinAsGuest` に `exchangeToken` の引数を加える。`/join` 画面は URL の `x` を保持して渡す。

### 10-7. 名刺交換を使えない人・組み合わせ

- **ゲストは名刺交換を使えない。** 名刺交換のタブを出さず、`createExchangeToken` も呼べない。ゲストが名刺交換QRを読み取ったときは 10-4 の2. の案内を出し、何も作らない（出会いの記録も残さない）。
- **連携コミュニティをまたぐつながりは、ルートのイベントの中で作る。** ルートのイベントに参加できるのは正規の会員なので、連携コミュニティだけのメンバーがルートのイベントの名刺交換QRを読み取ったときは 10-4 の6. の案内を出し、何も作らない。
- 連携コミュニティのイベントでは、そのメンバーどうし（正規の会員か、連携コミュニティだけのメンバーかを問わない）でつながれる。
- イベントの外（トークンが無い・期限切れ）では、つながれる範囲（`canDiscover`）の中でだけコネクト申請になる（10-4 の8.）。範囲の外なら何も作らない。
- v0.2 の `qr-blocked`（つながれない相手との出会いの記録）は廃止した。

### 10-8. 会場モード・イベントとの連携

- 名刺交換は、いつもイベントの中で行う（10-1）。見せる側はイベントを選んでQRを出し、そのイベントは交換トークンに入る（`createExchangeToken({ eventId })`）。`exchangeConnect` はトークンからイベントを決め、読取者をチェックイン（公式）または参加者に追加（プライベート）してから、両者の出会いの記録の `eventIds` に加える。
- 会場モードから名刺交換の画面を開いたときは、そのイベントを選んだ状態にし、変えられないようにする。
- 名刺QR（F4）をイベントの中で読み取ったときは、`cardConnect` に `eventId` を渡す。両者がそのイベントの参加者なら `eventIds` に加える（13-4 の7.）。
- F3 のつながり一覧の絞り込みに「イベント」を加える（場面ラベルより優先して表示）。
- 会場モードの一覧に、つながり済みの印を出す（自分の connections と照合）。

## 11. F2: 出会いの記録

### 11-1. 内容

相手ごとに1件、本人だけが見られる記録を持つ。

| 項目 | 型 | 説明 | 書く人 |
|---|---|---|---|
| partnerId | string | 相手の会員ID（ドキュメントIDと同じ） | Functions |
| firstMetAt | Timestamp | 最初に名刺交換した日時 | Functions |
| lastMetAt | Timestamp | 最後に名刺交換した日時 | Functions |
| eventIds | string[] | 会ったイベント（重複なし、新しい順、最大50件）。名刺交換・イベント中の名刺QRで加わる | Functions |
| labels | string[] | 場面ラベル（重複なし、新しい順、最大20件）。名刺交換ではイベントのタイトルが入る | Functions／本人 |
| via | string | 最初のきっかけ: `qr-exchange` / `qr-request` / `card` / `invite` / `request` | Functions |
| note | string | 自分用メモ（最大500文字） | 本人 |
| updatedAt | Timestamp | 最終更新 | 両方 |

- 保存場所: `tenants/{tenantId}/members/{memberId}/encounters/{partnerId}`
- **読み書きできるのは本人だけ。** 管理者（事務局）も読めない（ルールで本人に限る）。
- 本人がクライアントから更新できるのは `note`・`labels`・`updatedAt` だけ（ルールで項目を限定する）。それ以外は Cloud Functions が書く。`eventIds` は本人も変えられない（イベントで会ったことの記録のため）。
- メモは会話ではないため、エンドツーエンド暗号化の対象外とする。ただしルールで本人以外は読めない。メモ欄の下に「メモはあなただけが見られます」と表示する。

### 11-2. 既存の流れからの記録

- 招待（QR・招待の送付）から参加したとき: 両者に `via: 'invite'` で作る（`connectWithInviter` に追記）。
- コネクト申請が承認されたとき: 記録が無ければ両者に `via: 'request'` で作る（`respondToConnectionRequest` に追記）。
- 既存のつながりの分は、移行スクリプト `migrate:encounters` で作る（firstMetAt と lastMetAt は connection の respondedAt、無ければ createdAt。via は既存の invites に記録があれば `invite`、なければ `request`）。

### 11-3. 編集

- F3 の詳細画面と、10-5 の読み取り後の画面で、メモを編集できる。
- 場面ラベルは F3 の詳細画面で追加・削除できる（自由入力。自分が過去に使ったラベルを候補に出す）。

## 12. F3: つながり一覧

### 12-1. 画面（`/connect/list`、ナビ: つながる > つながり）

- つながり（`connections` で status が accepted のもの）を一覧する。
- 1行に表示するもの: プロフィール写真（大きめ、56px 以上）、名前、最後に会ったイベント（無ければ最後の場面ラベル）と日付（例:「2026年度 総会・懇親会（2026/11/8）」）、メモの1行目。
- 並び順: 「最近会った順」（lastMetAt の新しい順。記録が無いものは最後）と「名前順」を切り替える。
- 絞り込み:
  - イベント（自分の記録の `eventIds` にあるイベントから選ぶ。新しい順）→「あの総会で会った人」を一覧できる。場面ラベルより上に出す
  - 場面ラベル（自分の記録にあるラベルの一覧から選ぶ）
  - 名前・メモの文字で検索する（クライアント側で絞り込む）
- 30件ずつ読み、「もっと見る」で続きを読む。
- 申請中（`qr-request`・`card` で、まだ承認されていない相手）は、一覧の最後に「申込中」として分けて表示する。

### 12-2. 詳細（`/connect/list/:memberId`）

- 相手のプロフィール（公開範囲は既存のプロフィール公開設定に従う）
- 出会いの記録: 最初に会った日、会ったイベントの一覧（タップでイベント詳細へ）、場面ラベルの一覧、メモ（編集できる）
- 「トークを開く」ボタン

## 13. F4: 名刺に印刷するQR

### 13-1. 狙いと考え方

- 紙の名刺の裏などにQRを印刷しておけば、名刺を渡すだけでアプリでのつながりにつなげられる。後日、名刺入れから出して読み取ってもよい。
- 紙の名刺は長く残り、多くの人の手に渡り、本人の目の届かない所でも読み取られる。そのため、名刺交換QR（F1）のように「読み取っただけでつながる」ことはしない。**会員が読み取ったら、つながりの申し込み（相手の承認が必要）**にする。
- 名刺は刷り直しに費用と時間がかかる。そのため、名刺QRは**招待QRとは別のコードとして持つ**。画面の招待QRを作り直しても、印刷した名刺は使える。
- 印刷に向くよう、URL を短くしてQRの細かさを抑える（13-3）。
- 名刺QRは、イベントの外でも使える。

### 13-2. 画面（`/connect/card`、ナビ: つながる > 名刺QR）

- 招待先（ルート／所属する連携コミュニティ）を選ぶ（`InviteTargetPicker`）。名刺QRは招待先ごとに1つ。
- 表示するもの:
  - 名刺QRのプレビュー（中心にロゴを重ねない。印刷で小さくなっても読めるようにするため。誤り訂正は M）
  - QRの下に添える文の例:「TOKYO GIFU CONNECT でつながりましょう」（テナントのブランド名を使う）
- 操作:
  - **「QR画像をダウンロード」**: SVG（印刷会社に渡す用。拡大しても劣化しない）と PNG（1200px 四方）。ファイル名は `{ブランド名}-card-qr.svg` など。周囲の余白（クワイエットゾーン）を4セル分含める。
  - **「名刺の裏面データをダウンロード」**（13-5）
  - **「このQRを使えなくする」**: 名刺を紛失したとき・いたずらに使われたとき用。確認のため「使えなくする」と入力させる。使えなくすると新しいコードを作る（古い名刺は使えなくなるので、刷り直しが必要と明記する）。
- 設定（招待先ごと）:
  - **「はじめての方が、この名刺から参加できるようにする」**（初期値: オン）。オフにすると、アカウントのない人は参加できず、「お渡しした会員に招待を依頼してください」と表示する。
  - **「会員からの申し込みを自動で承認する」**（初期値: オフ。13-4 の5.）
- 印刷の目安を表示する:「QRは 15mm 四方以上で印刷してください。白い背景に黒で印刷してください」
- 招待QRを出せない人（ゲスト）には、この画面を出さない。

### 13-3. URL とコード

- URL: `https://{テナントのドメイン}/c/{名刺コード}`
  - 名刺コードは、推測されにくい英数字10文字（紛らわしい文字 `0 O 1 l I` を除く）。
  - 例: `https://connect.apgifu.org/c/7Kp3xR9mQa`（35文字前後。QRはバージョン3程度に収まる）
- 保存: `cardCodes/{名刺コード}` に tenantId、memberId、communityId?、active、allowJoin、autoAccept、createdAt、revokedAt? を持つ。Cloud Functions 専用（ルールで読み書きとも禁止）。
- 会員・招待先ごとに有効な名刺コードは1つ。作り直すと古いコードの active を false にする。
- 使えなくなった名刺コードを開いたとき:「この名刺のQRコードは使えなくなっています。お渡しした方にご確認ください」。

### 13-4. 読み取ったときの処理

`/c/{名刺コード}` を開いたとき、またはアプリ内の読み取り（F1）で名刺QRを読んだとき。

**ログインしていない（カメラアプリから開いた）とき**
- 名刺の持ち主の名前と招待先のコミュニティ名・ロゴを表示する（既存の参加画面の「誰からの招待か」と同じ範囲。写真やプロフィールはログインするまで出さない）。ページには `noindex` を付ける。
- ボタンを2つ出す:
  - 「はじめての方（参加する）」… allowJoin がオンのときだけ。既存の参加の流れへ。
  - 「会員の方（ログインしてつながる）」… ログイン画面へ。ログイン後にこのページに戻り、下の「会員が読み取ったとき」の処理を行う。

**はじめての人（アカウントなし）**
- 既存の参加の流れ（電話番号の確認 → 名前とログインID → ゲストとして参加）を使う。招待した人＝名刺の持ち主。
- 招待QRと同じく、持ち主とのつながり（承認済み）と1対1のトークを作る。名刺を手渡ししたこと自体を、紹介とみなす。
- 出会いの記録を両者に作る（`via: 'card'`）。
- 持ち主に「名刺から○○さんが参加しました」と通知する（既存の「招待から参加したとき」の通知を使い、文だけ変える）。
- `invites` には `via: 'card'` で記録する。

**会員が読み取ったとき** — Cloud Functions `cardConnect({ code, eventId? })`

読み取ると、つながりの申し込みになる（持ち主が自動承認をオンにしていれば、すぐにつながる）。

1. 名刺コードから持ち主とテナントを解決する。テナントが違う・自分の名刺・どちらかが停止中は、F1 と同じエラーにする（10-4 の4.）。
2. 読取者がゲストなら、10-4 の2. と同じ案内を出し、何も作らない。
3. 連携コミュニティあての名刺で、読取者がその連携コミュニティのメンバーでない場合は、10-4 の6. と同じく、連携コミュニティへの参加を先に案内する（`needsCommunityJoin`）。
4. `canDiscover` が false のときは、「この方とは、県人会のイベントで名刺交換するとつながれます」と表示し、何も作らない（`blocked`）。
5. つながり:
   - すでにつながっていれば、出会いの記録だけを更新する（`alreadyConnected`）。
   - 持ち主が autoAccept をオンにしていれば、つながり（accepted）と1対1のルームを作る（`connected`）。
   - それ以外は、既存の `sendConnectionRequest` と同じ処理でコネクト申請（pending）を作る（`requested`）。申請には「名刺から」と分かる印（`source: 'card'`）を付け、持ち主の申請一覧と通知で「名刺から申し込みがありました」と表示する。
6. 出会いの記録: 読取者側はその場で作る（`via: 'card'`）。持ち主側は、つながりが成立したとき（自動承認、または申請の承認時）に作る。
7. **イベントの中で読み取ったとき**（F1 の名刺交換の画面でイベントを選んでいるとき、または会場モードから）: `eventId` を渡す。読取者と持ち主の両方がそのイベントの参加者（公式のイベントはチェックイン済み、プライベートイベントは参加者）で、交換できる時間の中なら、出会いの記録の `eventIds` にイベントを加え、場面ラベルにイベントのタイトルを加える（持ち主側は、つながりが成立したときに加える）。条件を満たさなければ、イベントを付けずに処理する。名刺QRでは、イベントの中でも申し込み（または自動承認）の扱いは変えない。
8. 結果の画面は 10-5 と同じ（メモ欄、「続けて読み取る」）。

- 同じ人から同じ持ち主へのコネクト申請は、既存どおり1件だけ（重複は作らない）。
- 名刺コードあたりの読み取り処理は1時間に60回までとする（超えたら「しばらくしてからお試しください」）。

### 13-5. 名刺の裏面データ（印刷用 PDF）

デザインを自分で用意しなくても、そのまま印刷会社や家庭のプリンタで刷れるデータを出す。

- サイズ: 日本の標準名刺 91mm × 55mm。塗り足し3mm を含めた 97mm × 61mm の PDF を1枚。あわせて A4 に10面付けした PDF（家庭のプリンタ・市販の名刺用紙向け）も選べる。
- レイアウト（裏面、横向き）:
  - 左: テナントのロゴ（連携コミュニティあてなら連携コミュニティのロゴも並べる）、ブランド名、「でつながりましょう」の一文、本人の名前
  - 右: 名刺QR（20mm 四方）
- 文字の大きさは 7pt 以上。配色はテナントのブランドの色（未設定なら黒と白）。
- クライアント側で作る（PDF を作るライブラリは `pdf-lib` を想定。会場タグの札の PDF と共通にする）。日本語フォントは、表示に使う文字だけを埋め込む。
- 表面（住所・電話番号など）は扱わない。各自の既存の名刺の裏面として使う想定。

## 14. 管理画面

### 14-1. イベント（`/admin/:scope/events`）

- 既存の管理画面の対象（`:scope` = root または連携コミュニティのID）ごとに、その所属のイベントだけを一覧・作成・編集する。連携コミュニティの管理者は、自分の連携コミュニティの分だけを扱える。
- 一覧: タイトル、日時、状態、名簿の人数（アプリ登録あり）、チェックイン数。
- 作成・編集: 6-1 の項目と、使う会場タグの選択（9-1）、ホストの選択と、会いたい・話し相手の募集・ご紹介のオン・オフ（8章）。
- 参加者画面（`/admin/:scope/events/:eventId`）:
  - **名簿のインポート**（6-2）: ひな形のダウンロード、CSV のアップロード、取り込み前の確認、取り込み直し。
  - 名簿の一覧と人数。行ごとに、名前・ふりがな・区分・結び付けの状態（アプリ登録あり／名前だけ一致／アプリ未登録）・チェックインの状態と時刻・チェックインの方法を表示する。状態で絞り込める。
  - 1行ずつの追加・修正・削除、結び付けの確定・付け替え・解除。
  - 管理者によるチェックイン（9-6）と、チェックインの取り消し。
  - 会場での参加の申し込み（9-5）の記録（承認・お断り・取り消し、承認したホスト）。
  - **出欠の CSV ダウンロード**（名前・ふりがな・区分・アプリ登録の有無・チェックイン・チェックインの時刻）。事務局が総会の出席簿として使うため。インポートした電話番号・メールアドレスは含めない。
  - 当日の「いま会場にいる人数」と、テーブルごとの人数（受付の運営用）。
- 公開したとき、名簿に結び付いた人に通知するか選べる（初期値: 通知する）。名簿を取り込む前に公開した場合は、取り込んで新しく結び付いた人にも、取り込みのときに通知するか選べる。

### 14-2. 会場タグ（`/admin/:scope/venue-tags`）

- 一覧: 種類、ラベル（受付／テーブル番号）、状態（有効／使えない）、最後に読まれた日時。
- 操作: まとめて作る（9-2）、ラベルの変更、使えなくする、NFC への書き込み（Android の Chrome のみ）。
- **札の PDF**:
  - テーブル用: A6 の三つ折りのテーブル立て（テント型）。両面に、テーブル番号（大きく）、QRコード（30mm 四方以上）、「ここにスマホをかざす」の NFC の目印、テナント（または連携コミュニティ）のロゴを入れる。NFC シールを貼る位置を点線で示す。
  - 受付用: A5 の札。「受付 ― スマホをかざしてチェックイン」とQR。
  - PDF はクライアント側で作る（名刺の裏面データ（13-5）と同じく `pdf-lib` を想定）。

### 14-3. プライベートイベント（`/admin/root/private-events`）

- ルートの管理者だけが開ける。
- 一覧: タイトル、作成者、日時、参加者数、状態。参加者の名前とメモは見せない（5-4）。
- 操作: 中止（不正利用への対応）。

### 14-4. 名刺QR（事務局向け）

- 管理画面の会員詳細に「名刺QR」を表示し、管理者が代わりに名刺の裏面データ（13-5）をダウンロードできるようにする（スマホの操作が苦手な会員の名刺を、事務局がまとめて手配するため）。
- 管理者は、会員の名刺QRを使えなくすることもできる（不正利用の報告があったとき）。
- 管理画面の会員一覧に「名刺から参加」の数を出すかは今後検討する。

## 15. データモデル

**追加（イベント）**
- `tenants/{tenantId}/events/{eventId}`
  - kind（`official` / `private`）
  - scope（`{ type: 'root' }` か `{ type: 'community', communityId }`。private は常に root）
  - scopeKey（文字列。`root` か連携コミュニティのID。一覧の問い合わせとルールの判定に使う）
  - title、description、imagePath?、startAt、endAt、venue（name、address、mapUrl?）
  - checkInOpensAt、checkInClosesAt、attendeeListUntil
  - status（`draft` / `published` / `cancelled`。終了は時刻で判定）
  - hosts（ホストの会員ID一覧）、features（meet、help、intro の各オン・オフ）
  - tagCodes（使う会場タグのコード一覧）
  - counts（roster: 名簿の人数、linked: アプリ登録あり、checkedIn: チェックイン済み。Functions が更新する。private は checkedIn に参加者数を入れる）
  - rosterImportedAt?（最後に名簿を取り込んだ時刻）
  - createdBy、createdAt、updatedAt
  - private で使う項目: title、startAt、endAt、venue（name だけ）、description、status（`published` / `cancelled`）、checkInOpensAt、checkInClosesAt、attendeeListUntil、counts、createdBy。それ以外の項目は持たない
- `tenants/{tenantId}/events/{eventId}/roster/{rowId}`（参加者名簿の1行。official だけ。6-2）
  - name、kana?、category?（区分）
  - memberId?（結び付いた会員）、linkStatus（`linked` / `nameMatch` / `unregistered`）、linkedVia?（`import-phone` / `import-email` / `self` / `invite` / `host` / `admin`）、nameMatchIds?（名前だけ一致の会員ID。本人の確認に使う）
  - checkedInAt?、checkedInVia?（`nfc` / `qr` / `tag` / `exchange` / `invite` / `host` / `admin`）、checkedInBy?（代わりにチェックインしたホスト・管理者）
  - source（`import` / `onsite` / `admin`）、createdAt、updatedAt
- `tenants/{tenantId}/events/{eventId}/rosterPrivate/{rowId}`（名簿の行の、参加者に見せない項目。管理者と Cloud Functions だけ）
  - phone?（E.164）、email?、adminNote?
  - 終了から30日後（`attendeeListUntil`）に phone・email を消す。adminNote はホストも読める（17章）
- `tenants/{tenantId}/events/{eventId}/joinRequests/{requestId}`（会場での参加の申し込み。9-5）
  - rosterRowId、name（選んだ名簿の名前）、confirmCode（確認の4桁）、phoneLast4、status（`pending` / `approved` / `rejected` / `expired`）、createdAt、decidedAt?、decidedBy?（ホスト）、memberId?（承認で作った会員）
  - 電話番号の全桁と、受け取りの合言葉のハッシュは、Cloud Functions 専用の `eventJoinSecrets/{requestId}` に置く
- `tenants/{tenantId}/events/{eventId}/participants/{memberId}`（名簿に結び付いた会員・プライベートイベントの参加者の記録）
  - memberId（コレクショングループの問い合わせ用。ドキュメントIDと同じ）
  - rosterRowId?（official で、結び付いた名簿の行）
  - status（official: `registered` / `checkedIn`。private: `walkIn`）
  - checkedInAt?、checkedInVia?（名簿の行と同じ値を写す）
  - joinedVia?（private だけ。`creator` / `exchange`）、invitedBy?（private で、読み取ったQRを見せていた人）。private では、参加した時刻を checkedInAt に入れ、参加者を「出席済み」として扱う（17章の参加者の読み取りの条件がそのまま使える）
  - hideFromList（初期値 false）
  - showInPreview（初期値 true）、meetRequestsEnabled（初期値 true）、welcome（初期値 false）、talkTopic?（30文字まで）、isFirstTime（Functions が設定）
  - displayName、photoPath?（会場モードの一覧用の写し。結び付けたとき・チェックイン時に書き、プロフィール変更時は `recomputeDerivedProfiles` で更新する）
- `tenants/{tenantId}/events/{eventId}/seats/{memberId}`（テーブルの情報。17章）
  - currentTable、tables（テーブルの履歴）
- `tenants/{tenantId}/events/{eventId}/meetRequests/{fromId_toId}`（8-2）
  - fromId、toId、reason?、note?、status（`pending` / `accepted` / `declined` / `met` / `cancelled`）、createdAt、respondedAt?
- `tenants/{tenantId}/events/{eventId}/helpRequests/{requestId}`（8-3）
  - requesterId、location（テーブルのラベルか自由入力）、note?、status（`open` / `claimed` / `done` / `cancelled`）、claimedBy?、createdAt、escalatedAt?、closedAt?
- `tenants/{tenantId}/events/{eventId}/introductions/{aId_bId}`（8-4）
  - aId、bId、reasons（共通点の文の一覧）、score、status（`introduced` / `skipped`）、by（ホスト）、at。提案そのものは保存せず、呼び出しのたびに計算する
- テナントの設定: `matchingFields`（学校・部活動・卒業年・出身地・年代・話せること に対応する項目ID）、`youngAgeGroupMax`（若手とみなす年代の上限。初期値 30代）
- `venueTags/{tagCode}`（Cloud Functions 専用。ルールで読み書きとも禁止）
  - tenantId、scope、kind（`reception` / `table`）、label、tableNo?、active、createdAt、lastTappedAt?

**追加（名刺交換・出会いの記録・名刺QR）**
- `exchangeTokens/{token}` … tenantId、memberId、inviteCode、communityId?、eventId、createdAt、expiresAt。Cloud Functions 専用（ルールで読み書きとも禁止）。
- `tenants/{tenantId}/members/{memberId}/encounters/{partnerId}` … 11-1 の項目（`eventIds` を含む）。
- `cardCodes/{名刺コード}` … tenantId、memberId、communityId?、active、allowJoin、autoAccept、createdAt、revokedAt?。Cloud Functions 専用（ルールで読み書きとも禁止）。

**変更**
- `connections` に `source?: 'card' | 'qr'`（申請のきっかけ。表示と通知の文に使う）。
- `invites` の `via` に `card` と `event`（会場での参加の承認、9-5）を加える。
- 変更なし: `rooms`、`inviteCodes`。

**インデックス**
- events の（kind, scopeKey, status, startAt）。
- roster の（linkStatus, kana）、（checkedInAt）。名簿の電話番号・メールアドレスでの照らし合わせは、取り込みのときに Cloud Functions が rosterPrivate を読んで行う。
- 自分が名簿に結び付いた公式のイベントと、参加したプライベートイベントは、participants のコレクショングループの問い合わせ（memberId）で探す。

**型と図**
- 型は `functions/src/models.ts` と `src/app/core/models/firestore.models.ts` の両方に加える（複製管理。必ず揃える）。
- `docs/firestore-data-model.md` のクラス図・コレクション一覧・ドキュメントIDの設計ルールを更新する。

## 16. 通知

既存の Web Push の種類に次を加え、マイページの通知設定で個別にオン・オフできるようにする。

**イベント**
- イベントの公開・名簿への掲載（管理者が「通知する」を選んだとき。名簿に結び付いた人だけに送る）
- 前日のお知らせ（名簿に結び付いた人に。開始の24時間前を目安に、スケジュール関数で送る）
- イベントの中止（名簿に結び付いた人に）
- 会場での参加の申し込み（そのイベントのホスト全員に。「○○さん（名簿: 区分）が参加の承認を待っています」。9-5）

**会場で若手を孤立させない機能**（8-6 の届け方で送る）
- 会いたいが届いた／会いたいが成立した／会う約束の相手が会場に来た
- 話し相手の募集（ホスト・声かけ歓迎の人だけ）
- 紹介された

**名刺交換・名刺QR**
- 名刺交換でつながった（提示者に「○○さんと名刺交換しました」）
- 名刺から参加した（既存の「招待から参加したとき」の通知の文を変える）
- 名刺からの申し込み（既存の「コネクト申請の受信」の通知の文を変える）

## 17. セキュリティルール

**イベント**
- `events/{eventId}`（kind が `private` のとき）
  - read: 作成者（createdBy）、参加者（`participants/{呼び出した人}` が存在する）、ルートの管理者。
- `events/{eventId}`（kind が `official` のとき）
  - read: status が `draft` 以外で、呼び出した人が表示範囲（5-2・5-3）に入るとき。`draft` は、その所属の管理者だけ。
    - ルート: 呼び出した人の区分が `member`（区分なしの昔からの会員を含む）、または `guest` で `participants/{呼び出した人}` が存在する（名簿に結び付いている）。
    - 連携コミュニティ: 呼び出した人の `communityIds` に scope の communityId が含まれる。
    - 判定は、呼び出した人の members ドキュメントを `get()` して行う（既存のルールの判定関数に合わせる）。
  - write: 不可（Cloud Functions のみ）。
- `participants/{memberId}`
  - read（自分の分）: 本人。
  - read（他の人の分）: そのイベントに自分が出席済みで、`attendeeListUntil` より前で、相手の `hideFromList` が false のとき。加えて、その所属の管理者（private では、ルートの管理者も読めない。5-4）。
  - update（自分の分）: `hideFromList`・`showInPreview`・`meetRequestsEnabled`・`welcome`・`talkTopic`（30文字以下）だけ。それ以外は Cloud Functions のみ。
- `roster/{rowId}`（参加者名簿）
  - read: 名簿に結び付いた人（`participants/{呼び出した人}` が存在する）で、`attendeeListUntil` より前のとき。そのイベントのホストと、その所属の管理者。
  - write: 不可（Cloud Functions のみ）。
- `rosterPrivate/{rowId}`: その所属の管理者だけが読める（ホストは Cloud Functions 経由で管理用メモだけを受け取る）。書き込みは Cloud Functions のみ。
- `joinRequests/{requestId}`: そのイベントのホストと、その所属の管理者だけが読める。書き込みは Cloud Functions のみ。
- `eventJoinSecrets`: `allow read, write: if false;`
- participants の他の人の `currentTable` は、一般の参加者には見せない。ルールで項目単位の読み取り制限はできないため、**テーブルの情報は participants から分け**、`events/{eventId}/seats/{memberId}`（currentTable・tables）に置く。seats は本人・ホスト・管理者だけが読める。会いたいの成立相手と募集を引き受けた人には、Cloud Functions の通知と `getPartnerLocation` で居場所を渡す。
- `meetRequests`: 受け取った側（toId）だけが読める。送った側は Cloud Functions（`listMyMeetRequests`）経由で読む（見送られたことを伏せるため、`declined` を `pending` として返す）。書き込みは Cloud Functions のみ。
- `helpRequests`: 募集した本人と、そのイベントのホスト・声かけ歓迎の人（自分の参加者の記録で `welcome` が true）が読める。status が `open` 以外になったら、本人と引き受けた人とホストだけが読める。書き込みは Cloud Functions のみ。
- `introductions`: そのイベントのホストと管理者だけが読める。書き込みは Cloud Functions のみ。
- `venueTags`: `allow read, write: if false;`

**名刺交換・出会いの記録・名刺QR**
- `exchangeTokens`・`cardCodes`: `allow read, write: if false;`
- `encounters`:
  - read: `request.auth` が本人（既存の本人判定の関数を使う）
  - create / delete: 不可（Functions のみ）
  - update: 本人かつ、変更する項目が `note`・`labels`・`updatedAt` だけ。`note` は500文字以下、`labels` は20件以下で各ラベル50文字以下

**ルールのテスト（エミュレータ）で確かめること**
- 連携コミュニティだけのメンバーが、ルートのイベントを読めない。
- ルートだけの会員が、連携コミュニティのイベントを読めない。
- ゲストが、名簿に結び付いていないルートのイベントを読めない。
- 出席していない人が、参加者を読めない。
- 名簿に結び付いていない会員が、名簿（roster）を読めない。ホスト以外の参加者が、名簿の電話番号・メールアドレス（rosterPrivate）と参加の申し込み（joinRequests）を読めない。
- プライベートイベントを、作成者・参加者・ルートの管理者以外が読めない。ルートの管理者が、プライベートイベントの参加者を読めない。
- 成立していない人が、他の人のテーブル（seats）を読めない。
- 出会いの記録を、本人以外（相手・他の会員・管理者）が読めない。本人が許可外の項目（`eventIds` など）を変えられない。

## 19. 利用者への配慮（60代以上の会員）

- ボタンと文字は大きくする（主要ボタンは高さ 48px 以上、本文 16px 以上）。会場モードも同じ。
- 名刺交換の操作は「見せる」「読み取る」の切り替えだけにし、読み取り後に確認のダイアログを挟まない。
- 自分のQRの画面では「画面を明るくすると読み取りやすくなります」と小さく案内する。
- 懇親会で続けて何人とも交換できるよう、読み取り後の画面から1タップでカメラに戻れるようにする。

## 20. 受け入れ基準

**公式のイベントとチェックイン**
1. ルートの管理者がルートのイベントを、連携コミュニティの管理者がその連携コミュニティのイベントを、それぞれの管理画面から作成・公開できる。連携コミュニティの管理者は、他の連携コミュニティやルートのイベントを作成・編集できない。
2. 会員には、5-2 の表のとおり、自分が所属するコミュニティのイベントだけが一覧に出る。直接 URL やルールの問い合わせでも、見えないイベントは読めない。
3. 管理者が名簿の CSV（Shift_JIS・UTF-8）を取り込むと、電話番号・メールアドレスが一致した行はアプリの会員に結び付き、名前だけ一致の行と、アプリ未登録の行が分かれて表示される。取り込み直すと、同じ人の行は更新され、チェックイン済みの行は消えない。
3a. 名簿に結び付いた人は、参加者一覧で、名簿の全員とその状態（チェックイン済み／アプリ登録あり／アプリ未登録）を見られる。電話番号・メールアドレスは見えない。名簿に結び付いていない会員は、名簿を読めない（ルールのテストで確認）。
4. 名簿に結び付いた人が受付の札に iPhone をかざすと、ブラウザが開き（必要ならパスキーでログインし）、確認なしでチェックインでき、名簿の名前が表示される。名前だけ一致の人は、名前を確かめてからチェックインできる。名簿に無い人は、受付に案内され、何も記録されない。札のQRをアプリ内で読んでもチェックインできる。Android の Chrome では、アプリ内で札にかざしてもチェックインできる。
5. テーブルの札でチェックインすると、会場モードで同じテーブルの人が先頭に出る。別のテーブルの札にかざすと、テーブルが移る。
6. 会場モードで、自分と共通点のある人の人数が表示され、タップでその人たちに絞り込める。相手が非公開にしている項目は共通点の判定に使われない。
7. 会場モードから名刺交換すると、両者の出会いの記録にそのイベントが付き、F3 でイベントで絞り込める。
8. 見られないイベントの札、受付時間外の札、使えなくした札を読んだときは、9章の案内が出て、何も記録されない。
8a. アプリ未登録の人が札を読み、名簿から自分の名前を選んで電話番号を確かめると、イベントのホスト全員に通知が届く。ホストの1人が承認すると、アカウントができ、名簿に結び付いてチェックインされ、申し込んだ端末がログインした状態になる。2人のホストが同時に承認しても、アカウントは1つだけできる。
8b. ホストが、名簿に無い人を会場で名簿に追加してチェックインできる。
9. ホスト・管理者が代わりにチェックインでき、管理者が出欠の CSV（電話番号・メールアドレスを含まない）をダウンロードできる。
10. 管理画面から会場タグをまとめて作り、テーブル立ての PDF をダウンロードできる。Android の Chrome で NFC シールに書き込み、ロックできる。

**会場で若手を孤立させない機能**
11. 名簿に結び付いた人は、参加予定の人（公開に同意した人）を共通点の多い順に見て「会いたい」を送れる。見送られても、送った側の表示は「届けました」のまま変わらない。
12. 会いたいが成立した二人がチェックインすると、互いに相手のテーブルが通知される。成立していない人には他の人のテーブルが分からない（ルールのテストで確認）。
13. 「話し相手を探しています」を押すと、ホストと声かけ歓迎の人に写真付きで通知が届き、最初に「行きます」を押した1人が引き受ける。本人には向かってくる人の写真が出る。5分で引き受け手がいなければホスト全員に再通知される。
14. ホストの「ご紹介」に、若手・初参加の人と声かけ歓迎の人の組み合わせが、共通点の理由付きで上位に出る。「紹介しました」で両者に通知と出会いの記録が残る。
15. 会場モードの各人に、共通点の要約・話せること・今日話したいこと・話しかけるひと言の例が出る。非公開の項目は使われない。

**プライベートイベント**
16. 正規の会員がプライベートイベントを作り、名刺交換QRを見せると、読み取った正規の会員が参加者になり、つながる。作成者と参加者だけがそのイベントを一覧と詳細で見られる。
17. ゲストと連携コミュニティだけのメンバーは、プライベートイベントを作れず、参加もできない。
18. プライベートイベントを中止すると、名刺交換QRを出せなくなる。すでにできたつながりと出会いの記録は残る。ルートの管理者は管理画面で中止できるが、参加者の名前は見られない。

**名刺交換（F1）**
19. 公式のイベントにチェックインした会員Aが名刺交換QRを見せ、会員Bがアプリ内で読み取ると、確認なしで A–B のつながり（accepted）と1対1のトークができる。A の画面に「Bさんとつながりました」が出る。B が名簿に結び付いていてチェックインしていなければ、その場でチェックインされる。
20. A と B の両方に出会いの記録ができ、`eventIds` にそのイベント、場面ラベルにイベントのタイトルが付く。
21. すでにつながっている A–B が再び交換すると、つながりは増えず、lastMetAt・eventIds・labels だけが更新される。
22. 名刺交換QRを撮影して6分後に読み取ると、その場のつながりにはならず、コネクト申請（pending）になる。
23. 印刷した招待QR（`x` なし）を会員が読み取ると、コネクト申請になる。
24. アカウントのない人が名刺交換QRをカメラアプリで読み取ると、既存どおりゲストとして参加でき、A との出会いの記録（イベント付き）ができる。
25. ゲストには名刺交換のタブが出ない。ゲストが名刺交換QRを読み取ると案内が出て、何も作られない。連携コミュニティだけのメンバーがルートのイベントの名刺交換QRを読み取ると案内が出て、何も作られない。
26. 交換できるイベントが無いとき、名刺交換の画面に「名刺交換は、イベントの中で使えます」と出て、自分のQRは見せられない。正規の会員には「プライベートイベントを作る」が出る。
27. 正規の会員Aがプライベートイベントを作って名刺交換QRを見せ、正規の会員Bが読み取ると、B がそのイベントの参加者になり、A–B がつながる。続けて B のQRを C が読み取ると、C も参加者になり、B–C がつながる。
28. イベントの交換できる時間の外では、そのイベントの名刺交換QRを出せない。
29. 別テナントのQR、自分のQRを読み取ると、エラーが出て何も作られない。
30. iPhone（ホーム画面に追加したアプリ）と Android の Chrome で、アプリ内の読み取りが動く。

**出会いの記録とつながり一覧（F2・F3）**
31. 出会いの記録は本人以外（相手・他の会員・管理者）から読めない（ルールのテストで確認）。本人も `eventIds` を変えられない。
32. つながり一覧で、イベントを選ぶと、そのイベントで会った人だけが写真付きで出る。

**名刺QR（F4）**
33. 名刺QRを会員が読み取ると、持ち主へのコネクト申請（「名刺から」の表示付き）ができる。持ち主が自動承認をオンにしていれば、すぐにつながる。
34. 名刺QRをアカウントのない人が読み取ると、ゲストとして参加でき、持ち主とのつながり・トーク・出会いの記録ができる。allowJoin がオフなら参加できない。
35. 招待QRを作り直しても、名刺QRは使える。名刺QRを使えなくすると、古いコードを開いたときに案内が出て、何も作られない。
36. 名刺の裏面 PDF（1枚・A4 10面）をダウンロードでき、印刷したQR（20mm）をスマホで読み取れる。

## 21. 実装の順番（案）

名刺交換はイベントの中だけで使うため、イベントの土台（プライベートイベント）から作り、名刺交換を早めに使えるようにする。会場タグ・会場モードなどの公式のイベントの機能は、その後に作る。

0. **イベントの土台**: `events`・`participants` の型・インデックス・ルール・ルールのテスト（15・17章のうち、kind・プライベートイベント・participants に関わる部分）。プライベートイベントの作成・変更・中止と画面（5-4、`/events/new`・`/events/:eventId` のプライベート分、7-1 のプライベート分）
1. **名刺交換の土台**: `exchangeTokens`・`encounters` の型・ルール・ルールのテスト。`connectWithInviter` の切り出し、`createExchangeToken`・`exchangeConnect`・`listMyExchangeEvents`、関数のテスト
2. **名刺交換の画面**（見せる・読み取る・読み取り後。10章）
3. **出会いの記録とつながり一覧**: 既存の流れへの追加（`joinAsGuest`・`respondToConnectionRequest`）と移行スクリプト（11章）、つながり一覧・詳細（12章）、名刺交換の通知（16章）
4. **名刺QR**（13章）: コード・設定・`/c/:code` 画面・`cardConnect`・ダウンロード（SVG・PNG）→ 名刺の裏面 PDF → 管理画面（14-4）
5. **公式のイベント**: データモデル・ルールの残り（15・17章）、管理画面の作成・編集・公開（14-1 の前半）、管理画面のプライベートイベントの一覧（14-3）
6. **参加者名簿**: 名簿のインポート・取り込み直し・1行ずつの編集（6-2・14-1）、会員画面のイベント一覧・詳細（7-1・7-2）、参加者一覧（7-4）、通知（16章）
7. **チェックイン**: 会場タグの管理（14-2）・`/e/:code`・`checkIn`（9-1〜9-4）、ホストによるチェックインと名簿への追加（9-6）、会場での参加の申し込みとホストの承認（9-5）
8. 会場モード（7-3）と、名刺交換・出会いの記録との連携（10-8）
9. 共通点の項目の対応づけ（`matchingFields`）と D 話のきっかけ → A 会いたい → B 話し相手の募集と声かけ歓迎 → C ご紹介（8章）
10. 参加者画面の残り（参加の申し込みの記録・CSV・当日の人数。14-1 の後半）
11. 札の PDF と、Web NFC での書き込み（9-2・14-2）
12. SPEC.md の更新（6章の置き換え、4章に名刺交換、1章の招待QRとの関係、未確定事項#19・#28）と firestore-data-model.md の更新

## 22. 要決定事項

**イベント**
1. **ルートと連携コミュニティの共催イベント**: 本書では、イベントは自分の所属するコミュニティの人にだけ見える。県人会が「同窓会メンバーも参加できる」イベント（SPEC.md 9章 C2 の案）を作れるようにするか。作る場合は、scope に「参加できる連携コミュニティ」の一覧を加える。
2. ~~**会員が企画するイベント**~~ → v0.3 で決定。正規の会員は、名刺交換のためのプライベートイベントを作れる（5-4）。会場タグのある、会員が企画する公開のイベント（グループ内のイベントなど）は、引き続き今後の検討とする。
3. ~~**ゲストの参加**: ルートのイベントの `guestsAllowed` の初期値をオンでよいか。~~ → v0.5 で、参加者は名簿で決めることにしたため不要（5-3）。
4. **参加者一覧を見られる期間**: 初期値の「終了から30日後まで」でよいか。期間を過ぎた後は、つながり一覧（F3）からだけたどれる。名簿の電話番号・メールアドレスも、この日に消す。
5. ~~**受付係**: 管理者以外の会員に「受付係」の役割を与え、代理チェックインと招待をさせるか。~~ → v0.5 で、イベントのホストが代わりのチェックインと会場での参加の承認を行うことにした（9-5・9-6）。
6. ~~**参加費の管理**~~ → v0.5 で、申込と参加費の管理はアプリの外で行うことにした（6-1）。
7. **プロフィール項目の追加（東京岐阜県人会）**: 「高校の卒業年」と「話せること」を追加するか。追加しない場合、期の差の表示と、話せることによる提案は使えない。
8. **若手の基準**: 「若手とみなす年代」の初期値（30代まで）でよいか。同窓会ごとに変えられるようにするか。
9. **機能の名前**: 「声かけ歓迎」「話し相手を探しています」「会いたい」「ご紹介」「ホスト」の呼び方。会長・若手の双方に違和感がないか、意見交換会で確かめる。

**参加者名簿と会場での参加**（v0.5 で追加）
15. **アプリ未登録の人の名前の公開**: 参加者一覧（7-4）で、アプリ未登録の人の名前も参加者に見せてよいか（紙の参加者名簿を配るのと同じ扱い）。見せない場合は、アプリ未登録の人は人数だけを出す。
16. **会場で承認した人の区分**: 名簿で「会員」とされている人も、承認ではゲストとして作り、正規の会員への切り替えは既存の会員登録の申請で行う方針でよいか。ホストが承認のときに正規の会員として作れるようにするか。
17. **承認したホストとのつながり**: 会場で承認した人と、承認したホストのつながり・トークを作らない方針でよいか（既存の招待では、招待した人とつながる）。
18. **名前だけ一致の本人確認**: 名前だけ一致の行を、本人の「はい」だけで結び付けてよいか（取り違えはホスト・管理者が訂正する）。ホストの確認を必須にするか。
19. **名簿の CSV の列**: 6-2 の列（名前・ふりがな・電話番号・メールアドレス・区分・管理用メモ）で、事務局の名簿から作れるか。テーブル番号（席次）の列も要るか。

**名刺交換・名刺QR**
10. ~~ゲスト・連携コミュニティの範囲外の人とも、リアルで QR を交換したらつながれるようにするか。~~ → v0.3 で決定（10-7）。ゲストは使えない。名刺交換はイベントの中だけで使い、連携コミュニティをまたぐつながりはルートのイベントで作る。
11. 交換トークンの有効期間（その場のつながり5分、参加30分）でよいか。
12. 名刺交換の通知を、既存の通知設定の中で個別にオン・オフできるようにするか。
13. 名刺QRからの参加（allowJoin）の初期値をオンにするか。名刺は本人の目の届かない所でも渡るため、オフを初期値にする考え方もある。
14. 名刺QRから会員が読み取ったとき、申し込み（承認が必要）を基本とし、自動承認は本人の設定に任せる方針でよいか。
